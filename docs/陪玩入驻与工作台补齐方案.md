# 陪玩入驻与管理闭环补齐方案

> 文档类型：方案设计（**待实施，本文档不含代码改动**）
> 编制依据：当前工作区前后端代码（行号为本文档编制时快照）、`需求分析说明书.md`、`docs/项目现状与优化建议.md`
> 编制日期：2026-09-17（v1） · 2026-09-17（v2，依据代码评审反馈修订，见第 11 节）
> 结论：**后端业务接口已具备完整能力，本次属于"前端可达性与页面补齐 + 1 个现存审核缺陷修复"改造，后端零改动即可打通申请入口**；唯一的后端可选项是管理端待审核计数。

## 1. 背景

用户（毕设作者）在演示准备中发现两个现象：

1. **陪玩没有申请入口**：以普通用户身份登录后，翻遍顶部导航、用户菜单、个人中心，都找不到"成为陪玩师"的入口。
2. **没有专门页面管理自己的陪玩项目**：即使知道地址手动输入 `/companion/application`，也会被弹回首页；进不了工作台，也就无从管理服务项目、档期和收益。

这两个现象不是"功能没做"，而是**入口被路由守卫锁死 + 两个页面确实缺失**。本文档给出行号级证据和补齐方案。

### 2.1 一个关键结论：后端是通的

- `POST /api/companion/applications` **没有任何角色限制**，只要求登录态 + 业务校验（`CompanionApplicationController.java:33`，`SecurityConfig.java:53-66` 未拦截该路径）。
- `GET /api/companion/applications/mine`、`GET /api/companion/profile` 同样只校验登录态，身份与数据范围由服务层用 `userId` 判定（`ApplicationService.java:56-97`、`CompanionProfileService.java:33-36`）。
- 陪玩师工作台各接口（服务/档期/订单/收益）也不做角色注解，而是校验"陪玩师资料是否存在"（`CompanionProfileService.requireProfile` → `COMPANION_NOT_APPROVED`）。

因此 **P1/P2/P3/P5/P6/P7/P8 全部可以在前端解决，后端一行都不用改**；P4 同样只需前端补一个管理页，复用已有接口。

## 3. 目标与非目标

### 3.1 目标

1. 普通用户在用户端**看得见、点得到、提交得了**入驻申请，并能随时查看审核进度与驳回原因。
2. 审核通过后**无需退出重登**即可进入陪玩师工作台。
3. 陪玩师有**专门页面**维护陪玩主页（展示名/简介/认证能力）与接单状态，并能在工作台内管理服务项目、档期、履约、收益。
4. 管理员能审核**服务项目**，使"建服务 → 审核 → 上架 → 用户可预约"闭环成立。
5. 全部改动可被 `需求分析说明书.md` 的 FR-P01~P09、FR-M06、FR-M07 逐条追踪，便于写入论文与答辩演示。

### 3.2 非目标（本次不做）

- 不新增业务接口、不改数据库表结构、不动订单/钱包/评价/客服/AI 模块。
- 不做真实提现、私信、推荐、抢单大厅等 `项目现状与优化建议.md` 第 4 节明确不扩展的内容。
- 不重构 `http.ts` 的全局错误提示策略，只增加一个**可选**的静默标记（见 5.6）。

## 4. 方案总览

补齐后的完整闭环（→ 表示用户操作，【】表示页面）：

```
游客 → 登录/注册【/login】
      → 用户端任意页面（顶部导航 / 用户菜单 / 个人中心 / 找陪玩页 CTA）
      → 【/become-companion 成为陪玩师】填写真实姓名、手机号、自我介绍、游戏能力、证明图片
      → 提交 POST /api/companion/applications  →  页面转为"审核中"
      ────────────── 管理员 ──────────────
      → 【/admin/audit 审核管理 · 入驻申请】通过（自动授予 COMPANION 角色 + 创建陪玩主页）
      ────────────── 用户 ──────────────
      → 回到【/become-companion】或刷新任意页面 → 守卫静默刷新角色 → 出现"陪玩师工作台"入口
      → 【/companion/profile 我的陪玩主页】维护展示名/简介/能力 + 切换接单状态（FR-P05/P06）
      → 【/companion/services 服务管理】新增陪玩项目 → 状态"待审核"
      ────────────── 管理员 ──────────────
      → 【/admin/audit 审核管理 · 服务项目】通过
      ────────────── 陪玩师 ──────────────
      → 服务管理页"上架" → 服务对用户可见
      → 【/companion/schedule 档期管理】设置可约时段 → 【/companion/orders 接单履约】→ 【/companion/earnings 收益】
      ────────────── 用户 ──────────────
      → 【/companions 找陪玩】搜到该服务 → 【/booking 预约】→ 支付 → 履约 → 评价
```

## 5. 详细设计

### 5.1 路由与守卫改造

**路由改动清单**（`frontend/src/router/index.ts`）

| 路由 | 现状 | 补齐后 | 说明 |
|---|---|---|---|
| `/become-companion` | 不存在 | **新增**：`views/user/BecomeCompanionView.vue`，用户端布局子路由，`meta: { title: '成为陪玩师', requiresAuth: true }`，**不设 `roles`** | 登录即可访问，游客跳登录并带 `redirect` |
| `/companion/application` | 陪玩师工作台子路由 | **改为 redirect** 到 `/become-companion` | 兼容旧链接、文档与答辩脚本 |
| `/companion` 默认子路由 | `redirect: '/companion/schedule'` | `redirect: '/companion/profile'` | 落地页改为"我的陪玩项目"门面 |
| `/companion/profile` | 不存在 | **新增**：`views/companion/CompanionProfileView.vue`，`meta: { title: '我的陪玩主页' }` | FR-P05/P06 专属页面 |
| `/companion` 父路由 meta | `{ requiresAuth: true, roles: ['COMPANION'] }` | 追加 `roleFallback: '/become-companion'` | 角色不足时兜底到此页，而不是丢弃到首页 |
| `/companion/services` 等 | 保持 | 保持 | 不变 |

**守卫改造**（`frontend/src/router/index.ts:170-192`），改动点两处：

```ts
// 1) 登录态恢复 + 角色即时刷新：角色不足时先静默刷新一次用户信息（解 P5）
if (requiresAuth && (!userStore.user ||
    (requiredRoles.length > 0 && !requiredRoles.some((r) => userStore.hasRole(r))))) {
  try {
    await userStore.refreshUser()
  } catch {
    if (!userStore.user) return { path: '/login', query: { redirect: to.fullPath } }
  }
}

// 2) 角色仍不足：按分区兜底，而不是一律回首页（解 P1）
if (requiredRoles.length > 0 && !requiredRoles.some((r) => userStore.hasRole(r))) {
  const fallback = to.matched
    .map((r) => r.meta.roleFallback as string | undefined)
    .find((p) => !!p)
  return { path: fallback ?? '/' }
}
```

**为什么安全**：`roleFallback` 只加在 `/companion` 上；`/cs`、`/admin` 未设置该 meta，角色不符时仍回 `/`，行为与现在完全一致，不会把管理员导到申请页。

### 5.2 页面一：成为陪玩师（用户端）

**文件**：`frontend/src/views/user/BecomeCompanionView.vue`（新建，布局归属 `/` 用户端，复用 `UserLayout` 的顶栏与页脚）
**需求**：FR-P01、FR-P02、FR-P03、FR-P04

**五态自适应**（一次加载后按判定顺序取第一个命中，页面形态互斥）：

| 判定顺序 | 数据来源 | 页面形态 |
|---|---|---|
| ① 已是陪玩师 | `GET /api/companion/profile` 成功 | 顶部"您已是陪玩师"卡片：展示名、评分、完成单数、接单状态 + 【进入陪玩师工作台】按钮，并保留历史申请时间线 |
| ② 申请审核中 | `GET /api/companion/applications/mine` 首条为 `PENDING` | 进度时间线 + `el-alert`："审核通过前无法使用陪玩师功能，请耐心等待"；**不显示表单** |
| ③ **已通过但资料未取到（竞态窗口）** | 首条为 `APPROVED`，但 ① 的 `myProfile()` 未成功 | 仍按"已通过"处理：展示"审核已通过"卡片 + 【进入陪玩师工作台】+【重新检测】按钮；**禁止显示表单**，避免用户再提交一次后靠 409 `COMPANION_ALREADY_APPROVED` 兜底 |
| ④ 已驳回 | 同上，首条为 `REJECTED` | 展示驳回原因 + **表单**，允许修改后重新提交（新记录，历史只增不改，FR-P04） |
| ⑤ 从未申请 | 申请列表为空 | 表单（首次申请） |

> ③ 是现有实现的逻辑盲区：`ApplicationView.vue:167` 的显示条件是 `!profile && latestApplication()?.auditStatus !== 'PENDING'`，只排除"审核中"，因此"已通过但资料尚未就绪"会落进表单分支。新页面不得照抄该条件，必须显式判定 `APPROVED`。

**表单字段与校验口径**（必须与后端注解一致，避免"前端放过、后端 400"）：

| 字段 | 控件 | 前端校验 | 后端约束（`ApplicationSubmitRequest.java`） |
|---|---|---|---|
| 真实姓名 | `el-input` | 非空、≤32 | `@NotBlank` `@Size(max=32)` |
| 联系手机号 | `el-input` | 非空、`^1\d{10}$` | `@NotBlank` `@Pattern("^1\\d{10}$")` |
| 自我介绍 | `el-input` textarea | 非空、≤1000 | `@NotBlank` `@Size(max=1000)` |
| 游戏能力 | 动态行：游戏下拉 + 区服 + 段位 + 擅长位置多选 | 至少 1 项；每项游戏/区服/段位必填；区服、段位 ≤50 | `@NotEmpty` + `List<GameCapabilityDto>`（`gameId` `@NotNull`、`server`/`rank` `@NotBlank` `@Size(max=50)`） |
| 证明图片 | 文本域（沿用现状） | 选填，按换行/逗号切分 | `List<String> proofUrls`，无必填 |

> 说明：现有 `ApplicationView.vue:198-200` 用"粘贴图片地址"的方式填写证明图片，与 FR-P02"上传证明图片"存在差距。本次**先保持行为不变**（避免扩大改动面）；如需对齐需求，可另开一项复用已有的 `uploadFile(file, 'certification')`（`frontend/src/api/file.ts:12`，分类约定见 `FileStorageService.java:18` 的 `avatar/certification/evidence/general`）。

**关键实现要点**

1. **状态探测必须静默**（解 P7）：判定 ①/③ 时会请求 `GET /api/companion/profile`，非陪玩师返回 `403 COMPANION_NOT_APPROVED`，**该错误走的是 axios 错误分支**（HTTP 403），不是"HTTP 200 + 业务错误码"分支。因此静默标记必须**同时覆盖响应拦截器的两个弹错分支**：`frontend/src/api/http.ts:45-48`（`code !== 'SUCCESS'` 分支）与 `:51-68`（HTTP 异常分支）。实现方式：
   - **推荐 · 前端静默标记**：给 `request` 增加可选配置 `silentError?: boolean`（用 `declare module 'axios'` 扩展 `AxiosRequestConfig`），两个分支命中该标记时都跳过 `ElMessage.error`。改动约 10 行，向后兼容，其它接口行为不变。新页面用 `request({ url: '/companion/profile', method: 'get', silentError: true })`。
   - *备选 · 后端聚合状态接口*：新增 `GET /api/companion/applications/status` 返回 `{ isCompanion, latestApplication, history }`，一次请求拿到全部状态，彻底不产生 403 探测。语义更干净，但新增后端接口面，与"最小可逆变更"原则相悖，**默认不采用**。
2. 判定 `code === 'COMPANION_NOT_APPROVED'` 时视为"还不是陪玩师"的**正常状态**，不是错误；其余错误码仍按常规提示。
3. **判定为已通过（① 或 ③）时顺手调用一次 `userStore.refreshUser()`**：该路由无 `roles` 要求，守卫不会自动刷新角色，不补这一步则"审核刚通过就停在申请页"的用户看不到顶部导航的"陪玩师工作台"入口（见 P5 补充说明）。
4. 提交成功后不跳转，原地刷新为"审核中"态并给出成功提示（与现有实现一致）。
5. 判定为已通过后提供"进入陪玩师工作台"按钮 → `/companion`。
6. **代码复用**：新建页与现有 `ApplicationView.vue` 的"游戏能力动态行 + 申请时间线 + 状态映射"高度重合，**直接迁移复用这两块代码**（保持后端字段名与校验口径一致），只在外面套新的五态判定与用户端布局，以压低回归面。`ApplicationView.vue` 保留至新页验收通过后再单独提交删除（见第 9 节）。

### 5.3 页面二：我的陪玩主页（陪玩师端）

**文件**：`frontend/src/views/companion/CompanionProfileView.vue`（新建）
**需求**：FR-P05、FR-P06（补齐 P3）

| 区块 | 内容 | 调用 |
|---|---|---|
| 状态卡 | 展示名、评分与评价数、完成订单数、认证状态、**接单状态一键切换**（可接单/忙碌/休息） | `GET /api/companion/profile`、`PUT /api/companion/profile/service-status` |

#### 5.4.1 审核 `reason` 口径修正（修 P8）

后端两个 `AuditRequest.reason` 均为无条件 `@NotBlank`（`CompanionApplicationAdminController.java:62`、`CompanionServiceAdminController.java:60`），**空串一律 400**。这是现存缺陷：`AuditView.vue:32,44` 的"通过"分支提交 `reason = ''`，因此现有"通过"按钮实际不可用。

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **A · 前端补齐口径（推荐）** | 点"通过"时提交固定非空文案（如 `"符合要求"`），或弹出可选的"审核意见"输入框、留空则用默认文案；驳回时仍强制填写 | 后端零改动、零测试改动 | **本次采用**。数据库 `audit_reason` 会记录"符合要求"，该字段本就要展示给申请人（`ApplicationView.vue:155` 的"审核意见"），语义成立 |
| B · 后端条件校验（后续可选） | 把 `reason` 改为可空，在服务层对"驳回"分支校验非空，并补一条"通过 + 空 reason 返回 200"的集成测试 | 改后端 2 个 DTO + 2 个服务 + 1 个测试类；需回归 | 语义更正确，但超出本次"前端补齐"边界，**记为后续独立任务**（届时同步删掉该方案 A 的默认文案） |

**验收要求**：修复后 `/admin/audit` 的"通过"必须真正生效（申请状态转 `APPROVED`、自动授予 `COMPANION` 角色、创建陪玩主页），且不再出现"驳回时必须填写原因"的错误提示。
