# 游戏陪玩系统：项目现状与优化建议

> 文档类型：架构现状审计与迭代建议
> 审计依据：当前工作区代码、设计文档、构建与测试命令输出
> 审计日期：2026-08-25
> 结论：后端业务模块已形成闭环，前端已具备主要路由与页面；下一阶段重点是端到端验收、生产安全收口、异常场景覆盖和答辩演示稳定性，不建议继续无边界扩展业务功能。

- 后端模块已覆盖认证、用户、目录、陪玩师、订单、钱包、评价投诉、文件、客服、AI、公告、通知、收藏、审计和管理端。

- 设计文档已明确模块边界、订单状态机、客服会话状态机、RBAC、幂等和文件存储方案。

## 2. P0：必须在答辩演示前收口

### P0-1 端到端核心链路验收

**目标：** 从真实浏览器走通“注册/登录 → 浏览服务 → 创建订单 → 模拟支付 → 陪玩师接单 → 开始/结束 → 用户确认 → 评价/投诉”的主链路，并保留截图或录屏证据。

**原因：** 当前后端测试覆盖良好，但项目缺少浏览器级自动化测试；前端 `package.json` 也没有 test 脚本，无法证明路由、接口字段、权限守卫和页面交互全部对齐。

**验收标准：**

1. 至少准备普通用户、陪玩师、管理员、客服四类演示账号或可重复初始化脚本。
2. 核心链路成功完成，订单状态和钱包流水前后一致。
3. 至少覆盖余额不足、档期冲突、重复支付、越权访问、投诉退款五个异常分支。
4. 测试结果保存为测试报告，失败时能定位到接口、页面或数据问题。

**依赖：** 后端提供稳定种子数据和接口契约；前端完成页面联调；tester 负责验收矩阵。

### P0-2 安全与部署配置收口

当前 `SecurityConfig` 使用 `allowedOriginPatterns("*")`，`application.yml` 将 `com.gameplay` 日志级别设为 `debug`。这适合本地开发，不适合部署演示；文件上传和 JWT 配置也需要在部署前进行最小权限复核。

**验收标准：**

- 开发、测试、演示配置分离；演示环境 CORS 仅允许前端来源。
- 演示环境关闭 SQL/业务 DEBUG 日志，避免密码、手机号、订单业务数据进入日志。
- JWT 密钥、数据库密码、文件目录全部由环境变量或本地未提交配置提供。
- 文件下载必须验证路径不能目录穿越；上传按扩展名、真实 MIME、大小和文件名随机化校验。
- 明确 Nginx 同源代理、WebSocket 转发、上传目录权限和数据库初始化步骤。

### P0-3 订单、钱包和定时任务的异常回归

现有 60 个后端测试通过，但答辩风险最高的仍是并发和重复请求。应补充针对 `OrderService`、`WalletService`、`OrderTimeoutScheduler` 的回归测试，重点验证数据库唯一键和事务回滚，而不是只验证正常流程。

**验收标准：**

- 同一支付幂等号重复请求只产生一条流水，余额只扣一次。
- 两个用户并发预约同一陪玩师重叠时段时最多一个订单成功支付。
- 拒单、超时关闭、投诉全额/部分退款、自动确认均不会重复退款或重复结算。
- 定时任务重复执行具有幂等性，失败后可重试。

### P0-4 权限与数据范围验收

前端路由角色守卫只能改善体验，真实权限仍依赖后端；需要形成越权测试清单，尤其是客服只能访问被分配/授权会话，普通用户只能访问自己的订单、投诉和客服记录。

**验收标准：**

- USER、COMPANION、CUSTOMER_SERVICE、ADMIN 分别调用不允许的接口均返回统一权限错误。
- 修改 URL 中的用户 ID、订单 ID、会话 ID 不能读取他人数据。
- 禁用账号、客服禁用、改密和注销后已有 JWT 立即失效。
- AI 不存在退款、改订单、调余额、审核、仲裁、封禁等写权限。

## 3. P1：建议在核心验收后优化

### P1-1 前端性能与构建质量

前端构建成功，但主 JS 包约 1.1 MB，已触发 Vite chunk warning。建议保留现有路由懒加载，并进一步按 Element Plus、工作台、管理端拆分公共 chunk；对 `@vueuse/core` 的 Rollup 注释告警进行依赖升级或构建配置处理。

**验收标准：** 首屏只加载用户端必要资源，客服/管理端代码不进入首屏；构建无项目自有代码告警；核心页面在本机演示环境打开无明显卡顿。

### P1-2 WebSocket 可靠性与降级体验

客服模块设计了心跳、重连和 REST 补拉，但应使用真实断网/刷新场景验证：消息先持久化再推送、重连后不重复、不丢失、已关闭会话不能继续发送。

**验收标准：** 断开 WebSocket 后发送失败有明确提示；重连按游标补拉；重复 `clientMsgId` 不重复落库；AI 异常可降级 FAQ 并转人工。

### P1-3 页面状态完整性

重点补齐所有页面的加载中、空数据、接口失败、无权限、重复提交和分页状态；金额统一显示“元”，接口继续使用“分”。不要只依赖按钮禁用，后端校验仍是最终防线。

**验收标准：** 每个 P0 页面至少有 loading/empty/error 三类状态；网络失败可重试；提交按钮防重复；后端错误码能转换为用户可理解的提示。

### P1-4 文档和代码基线同步

README 当前接口概览仍偏旧，只列出部分 API 模块；应同步当前客服、AI、评价、文件、公告、通知、收藏、审计和管理接口，并补充一键初始化、演示账号、测试结果和常见故障。

设计文档中的版本日期和当前实现应建立“需求编号—接口—页面—测试用例”追踪表，便于论文和答辩说明覆盖关系。

## 4. P2：当前明确不建议扩展

以下内容不影响当前毕业设计闭环，暂不投入开发：真实支付/提现、移动端、小程序、用户与陪玩师私信、语音视频、直播、推荐算法、抢单大厅、Redis、消息队列和微服务拆分。当前架构已经明确首期边界，继续扩展会增加验收面和部署风险。

## 5. 角色分工建议

| 角色 | 建议任务 | 交付物 |
|---|---|---|
| @backend | P0-2 安全配置分环境；P0-3 并发/幂等/定时任务回归；P0-4 越权测试 | 配置方案、测试类、验证命令与结果 |
| @frontend | P0-1 核心链路联调；P1-1 chunk 拆分；P1-3 页面状态补齐 | 联调清单、构建报告、页面验收截图 |
| @tester | 建立四角色端到端验收矩阵，覆盖 5 个异常分支 | 测试报告与缺陷清单 |
| @designer | 检查核心链路的 loading/empty/error/成功反馈和答辩演示路径 | 页面验收意见、演示流程 |
| @devops | 本机/答辩机一键启动、Nginx/WebSocket、数据库初始化和配置脱敏 | 部署说明、启动脚本、故障排查表 |
| @docs | 同步 README、接口清单和论文可引用的测试结果 | 文档更新提交 |

## 6. 建议迭代顺序

1. 先由 @tester 固化 P0 验收矩阵，避免各成员各测各的。
2. @backend 与 @frontend 根据矩阵完成接口和页面联调，发现契约冲突先记录后修改。
3. @backend 完成安全、并发、幂等和越权回归；@devops 同步演示配置。
4. @designer 检查演示路径和异常反馈；@docs 同步 README 与论文材料。
5. 最后执行一次完整构建、测试、浏览器验收和干净工作区检查，再进入 reviewer 审查。
