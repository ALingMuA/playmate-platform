## 2. 目标、范围与原则

### 2.1 目标

1. 将个人中心由当前以账号管理为主的页面，逐步演进为包含本人业务内容的个人主页。
2. 补齐陪玩师公开展示链路，围绕 FR-U05 展示公开资料、能力信息、可预约服务和评价；可约档期按独立后续阶段处理。
3. 建立本人主页、公开主页、陪玩师资料工作台之间的导航闭环，同时保留各自权限边界。
4. 把接口数据、统计口径、隐私字段、空态与异常态作为设计的一部分，避免只按线框填假数据。

### 2.2 范围

- `/profile`：登录用户本人个人主页，未来承载概览、订单、评价、收藏、钱包和设置；陪玩师额外显示“我的陪玩主页”内容入口。
- `/companions/:userId`：游客可访问的陪玩师公开主页；本人访问可获得到工作台的管理入口。
- `/companion/profile`：陪玩师资料编辑工作台，维持“维护资料”的定位，增加前往公开预览的入口。
- 仅讨论上述页面所需的前后端接口、数据呈现、交互、响应式和验证工作，不扩展到全站视觉重构。

### 2.3 实施原则

- 保留 Vue 3 + TypeScript + Element Plus、现有 Vue Router、后端 Spring Boot、既有 `global.css` 设计令牌及原型类体系；不引入新框架。
- 保留 `/profile`、`/companions/:userId`、`/companion/profile` 路由。公开陪玩主页继续允许游客访问；个人页要求登录；工作台维持 `COMPANION` 角色限制。前端守卫只负责体验，后端负责真实鉴权与数据范围。
- 先冻结数据契约和访问规则，再按依赖开发。展示字段必须有真实数据源；分页当前页数据不可冒充全量统计。
- 每个阶段独立形成代码变更、验证证据和回滚点；将来若进入实施，再按项目 Git 规则提交相关文件。本轮不提交任何内容。

### 3.1 设计时必须处理的事实差异

1. 已有方案里提到的 `GET /api/reviews/companions/{userId}` 与当前代码路径不一致。当前前端调用的是 `GET /api/reviews/companion/{companionUserId}`；实施阶段应以届时后端 Controller 和 Swagger/接口测试为准，不复制过时路径。
2. 当前 `CompanionProfile` 有展示名、简介、能力 JSON、评分汇总、完成单、接单状态和认证状态；头像属于用户资料，需要公开接口关联用户数据并做字段白名单过滤。
3. `capabilities` 的游戏、区服、段位和位置标签是可编辑的资料字段。当前核对未证明公开展示时存在逐项审核状态或可公开的段位证明图片。因此，在审核语义与图片访问策略明确前，不能将这些文字直接称为“已核验段位”，也不能公开申请材料中的证明文件。
4. 陪玩师整体 `certificationStatus` 与每项能力的证明审核是不同概念。公开徽章的含义须由业务规则明确，不能仅因字段名或线框标签推定为逐项认证。
5. 收藏视图当前只有陪玩师 ID、展示名、简介、评分、评价数、接单状态和收藏时间。若目标卡片需要头像、完成单、起价或标签，必须从其他已公开接口组合或扩充服务端契约，不能假定这些字段已在收藏响应中。
6. 订单、评价等接口分页结果的当前页条数不代表用户的总完成单数、总评价数或评分分布。精确统计应来自有明确定义的聚合接口；若过渡使用局部数据，必须在 UI 显示样本范围。

## 4. 阶段总览与依赖

```text
阶段 0 契约与基线冻结
        ↓
阶段 1 公开资料 API 与隐私边界
        ↓
阶段 2 陪玩师公开主页首期（资料、服务、评价、收藏入口）
        ↓
阶段 3 用户个人主页内容化（概览、订单、评价、收藏、钱包、设置）
        ↓
阶段 4 陪玩身份融合与导航互通
        ↓
阶段 5 公开档期与预约预填（独立后端依赖）
        ↓
阶段 6 可选增强（统计聚合、流水、响应式打磨；作品须需求变更）
```

阶段 0 是设计冻结门槛，不写业务代码。阶段 1 的公开 API 是阶段 2 的资料 Hero/简介/能力展示前置依赖。阶段 3 可在阶段 2 完成后实施，也可与阶段 2 并行开发，但收藏 API 的前端接入应共享同一服务封装和状态策略。阶段 4 依赖本人公开主页可用。阶段 5 不阻塞前四阶段的基本详情展示与服务预约。

## 5. 阶段 0：现状复核与数据契约冻结

### 目标

在开发前确定角色视图、字段白名单、统计口径、API 的既有/新增边界和各页面状态，避免实现过程中以线框占位补数据。

### 设计/实施任务

- 复核三条目标路由、现有页面、接口类型和权限守卫；建立逐模块的数据来源表，标注“已有接口”“拟新增接口”“展示依赖未满足”。
- 确定公开主页读取规则：陪玩资料不存在、资格暂停、用户账号不可公开、无服务、无评价等情形分别返回何种状态与页面提示。公开接口必须匿名可读，并限制返回字段。
- 确定认证徽章、能力文字、段位证明图片的真实含义。若暂时没有审核后能力数据模型，则本期公开能力文字但不宣称逐项已验证；证明图片继续沿用既有审核规则，不直接展示入驻申请材料。
- 确定订单数、评价数、收藏数、注册天数、价格起点、评分平均值和评价直方图的统计口径（时间范围、可见评价状态、服务状态、舍入规则）。
- 确定 `ProfileHero` 等公共组件的数据边界；决定它是纯展示组件还是承担动作槽位，避免个人和公开主页强耦合。
- 对照两个 HTML 线框，列出视觉意图与真实交互差异；决定小屏 Tab、侧栏、吸底预约条的最终优先级。

### 交付物

- 冻结版页面与视角矩阵。
- API 字段/分页/错误语义表及隐私字段白名单草案。
- 统计口径表、组件职责表、验收用例清单。
- 尚未决定的问题及其责任阶段，不在代码中先行猜测。

### 验收门槛

- 每个线框模块都能指向一个真实字段/API，或明确列入后续阶段/暂不展示。
- 游客、本人普通用户、本人陪玩师三种视角的可见和可操作内容明确。
- 认证信息与申请证明图片的公开规则没有歧义；敏感字段不会进入公开 DTO。
- API 路径以代码/接口文档复核，不以已有方案中的建议路径当作现存事实。

### 暂不做

不修改线框图、代码、接口或需求规格；不创造新的业务字段或估算数字来填充设计稿。

## 6. 阶段 1：公开陪玩资料接口与安全契约

### 目标

为游客可见的陪玩师主页提供独立、最小化、可公开缓存策略明确的资料查询能力。

### 拟议接口

`GET /api/companion-profiles/{userId}`（路径是建议名，需在阶段 0 冻结；不能与当前仅供本人访问的 `/api/companion/profile` 混用）。

建议 DTO 白名单：

| 字段 | 来源/说明 | 公开要求 |
|---|---|---|
| `userId` | 用户 ID | 用于页面路由/本人判断；不据此暴露其他个人资料 |
| `displayName` | 陪玩主页资料 | 空值按契约处理，不回退展示真实姓名 |
| `avatarUrl` | 用户头像资料 | 仅公开头像 URL；缺省时前端使用昵称首字兜底 |
| `profileIntro` | 陪玩主页资料 | 经过长度/安全规则校验；可为空 |
| `serviceStatus` | 陪玩资料接单状态 | 返回枚举；暂停/不公开情形按冻结策略处理 |
| `ratingAvg`、`ratingCount` | 已完成评价聚合字段 | 说明统计范围与精度 |
| `completedOrderCount` | 陪玩资料聚合字段 | 明确只统计完成订单 |
| `capabilities` | 游戏、区服、段位和位置标签 | 只有在确认展示语义后公开；不得默认等于“段位已核验” |
| `certificationStatus`（可选） | 陪玩师资格状态 | 仅用于明确业务徽章；是否对游客公开需阶段 0 确认 |

不返回真实姓名、手机号、邮箱、入驻申请全文、证明图片 URL、审核备注、登录信息、内部管理字段或陪玩师端维护数据中不属于白名单的字段。头像读取需在后端服务中显式选择允许字段；不要直接序列化 `User`、`Application` 或数据库实体。

### 实施任务建议

1. 依据现有用户/陪玩资料/账号状态实体确认公开查询的关联关系、可见条件及唯一性。
2. 新增只读公开 DTO、Service 查询和匿名 GET Controller；仅在“有资格公开且账号状态允许”的规则满足时返回资料。
3. 明确不可见资源的响应语义（建议对不存在与不允许公开统一使用 404，避免枚举账号；由全局错误码规范确认）。
4. 复用现有服务与评价聚合字段；服务数量和最低价格如在本接口返回，必须定义只统计已审核且在架服务，或继续由公开服务列表聚合。
5. 添加后端测试覆盖游客读取、正常公开、无资料、暂停/封禁、字段白名单和异常数据；验证没有敏感字段序列化。
6. 生成/更新接口文档，但仅在实现阶段执行。

### 验收门槛

- 匿名请求可读取符合公开条件的资料，不需要前端伪造身份或暴露管理接口。
- 对无资料、已暂停/封禁或不满足公开条件的账号按冻结后的响应策略处理。
- 响应中不包含真实姓名、手机号、邮箱、申请证明 URL 和审核备注；用序列化断言或集成测试验证。
- `capabilities` 的认证含义清楚；若现有数据无法支持“已核验”表述，则 UI/API 不使用该文案。
- 现有 `/api/companion/profile` 的角色鉴权与编辑行为没有被改成公开访问。

### 依赖/回滚

依赖阶段 0 的字段白名单和资格状态定义。若 DTO 泄露多余字段或匿名策略不符合预期，回滚新增公开路由和 DTO，不更改既有本人资料接口。

## 7. 阶段 2：陪玩师公开主页首期前端

### 目标

把 `/companions/:userId` 从 ID 占位的服务详情升级为可浏览、可预约、游客友好的公开主页，优先完成公开资料、服务和评价。

### 页面模块

1. **Hero 身份区**：展示名、公开头像、资格徽章（仅按已冻结语义）、接单状态、评分、完成单、在架服务数和起价。无服务但有公开资料时仍展示 Hero 与主页 Tab，不因服务列表为空而隐藏整页。
2. **主页 Tab**：简介、能力卡和服务标签；能力资料为空时用明确空态，不用示例段位填充。
3. **服务 Tab**：继续使用现有公开服务分页接口；服务卡显示服务名、游戏/类型、描述/标签、价格、最短时长；选择状态在 Tab 间保留。默认选择策略（最低价或第一项）在开发前确认，并且展示默认选择原因。
4. **评价 Tab**：复用现有公开评价分页 API；显示评分汇总、评价人/匿名名、星级、标签、内容和日期；增加符合后端支持的筛选与分页。
5. **关注动作**：访客未登录点击时引导登录并保存合理返回位置；已登录后使用收藏 API，成功后更新按钮；失败后恢复原状态并提示。
6. **预约动作**：复用现有 `/booking`，传陪玩师 ID、服务 ID；服务选择不丢失。此阶段尚无公开档期时不伪造“可约时段”。

### 前端模块建议

建议按职责新增或抽取 `ProfileHero`、`StatStrip`、`CapabilityCard`、`ServiceCardGrid`、`RatingHistogram`、`StatusDot`、`SectionSkeleton`、`GuidedEmptyState`；是否复用到找陪玩列表需避免扩大本阶段范围。新增 `api/favorite.ts` 和 `useFavorite` 前，先核对现有 API 返回分页结构、Pinia 用户态和登录跳转规范。

### 响应式与交互

- 桌面端优先采用主页内容区 + 能力信息侧栏；中等屏幕把侧栏变为内容上方的可横滑区域；小屏幕改为单列。
- 服务预约按钮桌面端可留在侧栏，小屏幕可吸底，但必须预留底部导航/安全区并避免覆盖内容。
- Tab 支持 URL hash 刷新恢复；切换后维持服务选中态与滚动体验。
- 骨架屏、无服务、无评价、请求失败、不可公开和登录引导分别设计，不用同一空白页代替。
- 尊重 `prefers-reduced-motion`；动效不能是表达状态的唯一方式。

### 验收门槛

- 游客和登录用户都能打开正常公开主页；本人查看时不把访客预约动作误认为管理入口。
- 有资料无服务、服务无评价、头像失败、接口失败和不可公开等状态可理解、可恢复。
- 服务卡数据来自 API；预约请求参数正确；切换 Tab 后所选服务仍然一致。
- 评分平均值与数量优先展示服务端聚合；直方图若只统计当前页，必须清晰标注“当前加载评价”而不得标为全部历史分布。
- 收藏操作登录拦截、增删成功、失败回滚均验证；其他页面状态同步范围在阶段 0 约定。
- 桌面、中等、小屏至少覆盖设计断点；键盘操作和可见焦点可用。

### 暂不做

暂不实现公开档期 API、段位证明图片公开、作品/动态模块、真实支付和私信/语音/直播。

## 8. 阶段 3：个人主页内容化与收藏前端

### 目标

在不丢失现有资料编辑、钱包、入驻状态和账号安全操作的前提下，把 `/profile` 变成面向本人的分区主页。

### 页面与数据分区

- **Hero**：头像、昵称、角色、账号状态和必要操作。订单数/评价数/收藏数/注册天数必须使用准确聚合字段；当前用户资料视图没有注册时间，不能在前端猜测注册天数。
- **概览**：资料完整度提示、最近若干订单、钱包概览、收藏横滑预览、陪玩中心入驻成长卡。每张卡提供明确的“查看全部/下一步”入口。
- **订单**：复用现有订单分页和状态筛选行为，优先抽取 `OrdersView` 可复用列表面板，不复制整套支付、取消、确认、售后操作逻辑。
- **评价**：复用 `myReviews` 分页，显示评价内容和关联订单入口。当前未发现用户删除评价接口，本期不增加删除按钮或承诺删除能力。
- **收藏**：首次接入 `GET /api/favorites?page=&size=` 与 POST/DELETE；支持分页、取消收藏、无数据引导到找陪玩。卡片只使用收藏 API 实际字段，若要头像/价格等丰富字段，单列为契约扩充，不做前端假拼装。
- **钱包**：首期展示当前 `walletMe` 支持的余额、冻结金额、累计收入。钱包收支流水若没有用户端分页接口则不在本阶段承诺展示。
- **设置**：保留个人资料编辑、改密、注销全部会话、退出登录现有逻辑和确认机制；设置分区只调整信息架构，不改鉴权和安全流程。
- **我的陪玩主页 Tab**：可在阶段 4 接入，避免普通用户看到空白管理内容。

### 统计策略

若要显示完整准确的 Hero 统计，建议新增一个聚合能力（例如 `GET /api/users/me/stats`，路径需按现有规范确认），并定义订单仅数 `COMPLETED`、评价数仅数有效已发布评价、收藏数为当前有效收藏、注册天数按账号创建时间与时区计算。若决定不增加聚合 API，则先隐藏缺少数据源的指标；不能用第一页条数或当前时间反推注册日期。

### 交互与加载

- Tab `概览/订单/评价/收藏/钱包/设置` 以稳定 key 同步 URL hash；首屏仅加载概览所需数据，其余分区首次访问加载。
- 资料、订单、钱包、收藏各自有独立 loading/error/empty 状态，单一接口失败不能清空其它成功区块。
- 收藏乐观更新需在重复点击、并发请求、请求失败和分页最后一项取消等情形下保持正确总数/当前页。
- 陪玩成长卡沿用现有申请状态识别与下一步路径，审核驳回原因仅本人可见；不改变五态业务状态机。

### 验收门槛

- 普通用户/陪玩师都能访问全部本人分区；陪玩师专属内容仅在资格已生效时显示。
- 已有编辑资料、改密、注销全部会话、登出、钱包和入驻路径可逐一回归。
- 订单状态筛选、分页、订单详情/支付/评价/投诉入口和原操作权限不回退。
- 收藏列表展示字段与响应类型一致；增删失败能恢复；访客未登录收藏行为正确引导。
- Hash 刷新恢复正确；Tab 懒加载不会重复发送无意义请求；错误提示不会屏蔽其他区块。
- 统计若已上屏，聚合口径有接口证据；缺失 `createdAt` 或总量时明确隐藏而非显示伪值。

## 9. 阶段 4：陪玩师身份融合与导航闭环

### 目标

连接个人主页、陪玩师公开主页和维护工作台，让陪玩师能预览真实公开效果，同时不把管理能力暴露给访客。

### 导航与内容

- `/profile` Hero 陪玩身份卡显示接单状态、展示名、评分和完成单；“预览公开主页”跳转 `/companions/:myUserId`。
- `/profile#tab=companion`（hash key 可在实现时确认）提供“我的陪玩主页”摘要：接单状态快捷入口、评分/评价/完成单/服务数、能力只读卡，以及“预览公开主页”“去工作台维护资料”两个入口。
- `/companions/:userId` 仅当当前登录用户 ID 与路径 ID 匹配时显示“编辑主页”；访客不渲染任何管理入口。
- `/companion/profile` 增加“预览用户端展示效果”入口；保留当前保存资料与接单状态操作，不改变管理页主要表单。
- 已完成订单详情、收藏卡片或找陪玩卡片的主页入口，仅在不扩大回归风险的情况下逐个纳入；本阶段最低闭环为个人主页、公开主页、工作台三处。

### 状态一致性

- 接单状态仍以 `updateServiceStatus` 响应为准；若使用乐观更新，失败时必须回滚状态并显示原因。
- 编辑保存后重新读取公开资料或使本地相关数据失效；不能因当前“无缓存”推断将来不存在缓存。
- 公开资料只读字段与本人工作台可编辑字段分离；工作台不应复用公开 DTO 执行写入。

### 验收门槛

- 陪玩师本人能按“个人主页 → 公开主页 → 编辑工作台 → 公开主页”完成往返。
- 普通用户没有工作台入口；游客在公开页看不到编辑入口；直接访问工作台仍受服务端角色权限保护。
- 更新展示名、简介、能力或接单状态后，公开视图按约定刷新；失败不会显示未持久化的成功结果。
- 不影响 `/companion` 工作台默认路由、角色兜底和现有表单验证。

## 10. 阶段 5：公开档期与预约时间预填

### 目标

补齐 FR-U05 的“可约时间”，让访客只能读取适合公开的档期摘要，并能从时段进入预约。

### 拟议接口

建议 `GET /api/companion-profiles/{userId}/availabilities?days=7`，需与当前档期模型和时区/时段规则对齐。公开响应只包含可以公开展示的 `AVAILABLE` 时段摘要，不包含备注、内部来源、管理记录或用户隐私；不得复用陪玩师本人档期管理端点给游客。

### 页面行为

- 未来 7 天以明确日期和时间展示可约时段；“不可约”仅在业务需要且数据足够时展示，避免把未配置误显示为不可约。
- 点击具体时段跳转 `/booking` 并传入陪玩师 ID、服务 ID、预约开始时间；预约页服务端仍重新校验时段、状态、服务可用性和最短时长。
- 已选服务在切换 Tab 后保留；未选择服务时的默认策略在阶段 0 冻结。
- 小屏吸底预约条显示已选服务、价格/单位和“去预约”，不直接创建订单。
- 服务状态为 BUSY、RESTING 或 SUSPENDED 时，根据规则禁用或引导用户，不以隐藏按钮替代清晰说明；后端必须拒绝不符合条件的预约。

### 验收门槛

- 匿名用户只能取得公开的可约时段；响应没有备注或管理字段。
- 时区、跨日边界、已过期时段、并发被占用时段及状态变更均有测试覆盖。
- 从时段进入预约页的时间正确显示；创建订单时后端再次校验，客户端预填不能绕过业务规则。
- 无档期、接口失败、非可接单和临时失效状态都有明确反馈。

## 11. 阶段 6：增强项与需求变更闸门

### 可选优化

- 用户统计聚合接口，替代客户端并行请求与不精确计数。
- 用户侧钱包收支流水分页及明细筛选；实施前先确认目前是否已有可用接口和数据权限。
- 评价评分直方图服务端聚合，避免只用当前页数据估算全量分布。
- 更多页面的 `CompanionCard` 复用、性能优化、动效和响应式细节打磨。

### 作品/动态模块的边界

需求分析说明书将动态社区、短视频、直播、礼物打赏等列为非目标。公开主页新增作品/动态属于需求变更，不能作为本方案默认实现项。只有完成范围评审后，才进一步设计数据模型、审核状态、文件访问、安全与隐私策略、接口和文档同步；是否新增表/Tab/上传功能另行确认。

### 验收门槛

- 每项增强都有独立范围、依赖和价值；可延期，不阻塞前述核心页面。
- 若作品/动态获批，需求分析、概要设计、详细设计和实现范围同步更新后再开发。
- 不把真实支付、提现、语音房、视频、直播、私信或游戏战绩自动同步纳入本次主页改造。

## 12. 跨阶段验证清单

### 功能与数据

- 游客、登录普通用户、登录陪玩师三种视角分别验证路由、字段和按钮。
- API 的成功、空数据、无权限、不可公开、分页边界、服务端错误和网络失败均验证。
- 收藏增删重复请求、失败回滚和页面间状态变化验证。
- 订单状态、评价可见状态、价格和评分的统计来源与口径可追溯。
- 任何提示“已保存/已更新”的状态都以服务端成功响应为依据。

### 安全与隐私

- 公开响应白名单测试：禁止返回真实姓名、联系方式、入驻证明 URL、审核意见和管理数据。
- 陪玩师工作台的读取与写入继续受登录及 COMPANION 角色约束；普通用户个人页受本人身份约束。
- 未登录关注/预约仅提供登录引导，不在客户端伪造操作成功。
- 对公开图片 URL、简介文本、评价文本继续遵循现有文件访问与内容安全策略。

### 视觉与可访问性

- 至少覆盖宽屏、平板/中等宽度和手机宽度；检查 Tab 溢出、侧栏重排、服务卡密度与吸底遮挡。
- 骨架屏、空态、错误态、图片失败回退符合页面信息层级。
- 键盘可操作，按钮有可读名称和焦点状态；颜色不是唯一状态提示。
- 开启 `prefers-reduced-motion` 后不依赖动画传达信息。

### 工程与发布

- 每阶段按影响范围执行后端测试、前端类型检查/构建、接口集成测试和浏览器走查；涉及匿名访问、权限或数据库时，单测/静态检查不能替代真实接口验证。
- 实施时记录基线 Git 状态，只提交本阶段相关文件；不得覆盖无关工作区改动。
- 阶段交付记录实际执行的测试、结果和未覆盖范围；设计文档本身不声明这些验证已通过。
