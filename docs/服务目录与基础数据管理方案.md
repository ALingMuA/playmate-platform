# 服务目录与基础数据管理方案

> 文档类型：方案设计（**待实施，本文档不含代码改动**）
> 编制依据：当前工作区前后端代码（行号为编制时快照）、`需求分析说明书.md`（FR-M10/M11/M12、FR-U01/U05、FR-P02/P07）、`docs/陪玩入驻与工作台补齐方案.md`
> 编制日期：2026-09-17（v1） · 2026-09-17（v2，据 v1 复核修订，见第 11 节）
> 结论：**陪玩师当前无法新增/修改/删除游戏、服务类型与标签**——这三类"服务目录"的写接口全部在管理员 `@PreAuthorize` 下。问题不是"陪玩决定了服务类型"，而是**管理端一个维护入口都没有**（后端 12 个管理接口在 UI 上完全不可达），目录只能停留在种子数据；同时陪玩侧有两处"看起来像自己定"的自由度、三类目录"物理删除无引用校验"的隐患，以及**停用游戏的收口只做了一半（列表隐藏、直接下单仍可通过，见 P4/P7）**，需要在补管理页面时一并收口。
> 实施顺序原则：**先加护栏，再开入口**（后端引用校验 → 管理页面），见 §8。

## 1. 背景

用户反馈：**服务类型和服务类别不应该由陪玩来决定，应该是管理员后台来管理。**

本文档先核实"陪玩到底能不能决定"，再给出"由管理员统一维护"的补齐方案。用户表述中的"服务类别"按 `TagCategory`（标签分类：POSITION/STYLE/HERO/OTHER）理解，与"服务类型"（`ServiceType`：开黑陪伴/娱乐陪玩/游戏教学）同属本次范围；游戏（`Game`）也是同一套基础数据，一并纳入。

## 2. 现状核实：陪玩现在能不能自己定？

**不能创建、不能修改、不能删除。** 写接口统统在管理员权限下，陪玩师侧只有"选择"能力：

| 行为 | 陪玩师 | 管理员 | 代码证据 |
|---|---|---|---|
| 新增/编辑/删除 游戏 | ❌ 无接口 | ✅ 有接口 | `AdminCatalogController.java:47-70`（类级 `@PreAuthorize("hasRole('ADMIN')")`，:36） |
| 新增/编辑/删除 服务类型 | ❌ 无接口 | ✅ 有接口 | `AdminCatalogController.java:75-99` |
| 新增/编辑/删除 标签 | ❌ 无接口 | ✅ 有接口 | `AdminCatalogController.java:104-129` |
| 公开读取（仅启用项） | ✅ 只读 | ✅ | `CatalogController.java:35-44`（游戏）、`:47-50`（类型）、`:56-59`（标签）；`SecurityConfig.java:56-57` 放行的是 GET 类路径 |
| 发布服务时**选择**游戏/类型 | ✅ | — | `ServiceManageView.vue:206`、`:211` |
| 自由填写服务标题/说明 | ✅ | — | `ServiceManageView.vue:216`、`:219` |
| **在后台维护上述基础数据** | — | **❌ 无页面** | `AdminLayout.vue:7-18` 菜单无目录项；`frontend/src/views/admin/` 无对应页面；`api/admin.ts` 无任何 catalog 封装（grep 为空） |

所以准确的说法是：**陪玩师没有"定义"目录的权力，但管理员也没有"定义"的手段**——目录被冻结在 `sql/data.sql:21-50` 的 3 个游戏、3 个服务类型、26 个标签（王者荣耀 8 个 + 英雄联盟 8 个 + 和平精英 4 个 + 通用 6 个，覆盖 POSITION/HERO/STYLE/OTHER 四类）上。`需求分析说明书.md` 里 FR-M11（服务类型管理，P0）与 FR-M10（游戏管理，P0）目前**零前端实现**，这是答辩会被直接问到的缺口。

## 3. 问题定位

| 编号 | 问题 | 代码证据 | 影响 |
|---|---|---|---|
| **P1** | **管理端零入口（核心）**：后端 12 个目录管理接口在 UI 上不可达 | `AdminCatalogController.java` 三个分组的 GET/POST/PUT/DELETE；前端 `AdminLayout.vue:7-18`、`views/admin/` 全目录、`api/admin.ts` 均无痕迹 | 服务类型/类别/游戏无法维护；FR-M10/M11 零实现；运营只能改数据库 |
| **P2** | **陪玩侧标签是"全量"加载**：发布服务时一次拉出所有游戏的标签 + 通用标签 | `ServiceManageView.vue:51`（`listTags()` 不传 gameId）→ `CatalogController.java:54-58` 注释与 `TagService.java:38-46`：gameId 为空即返回全部 | 陪玩师可给"王者荣耀"服务挂上"上单/盲僧"（英雄联盟标签），"类别"语义被稀释——这正是"看起来像陪玩自己定类别"的直接来源。**对照**：申请页与主页的能力标签是按游戏过滤的（`BecomeCompanionView.vue:123`、`CompanionProfileView.vue:60,79`） |
| **P3** | **三类目录都是物理删除且无引用校验**（后端注释自认 TODO） | `GameService.java:93-102`（注释："后续服务/订单模块接入后，此处应校验是否存在关联的陪玩服务或有效订单（停用优先，不允许直接删除）"）、`ServiceTypeService.java:82-87`、`TagService.java:103-108` | 服务/订单模块**早已接入**，校验却没补。当前因无 UI 入口而未暴露；**一旦按本方案补上管理页面，管理员删一个被引用的游戏就会产生脏引用**（`CompanionServiceService.java:204` 取不到游戏时回落空串，历史订单靠快照但列表会显示空白） |
| **P4** | **停用语义不完整**：停用游戏只拦"新建/编辑服务"，拦不住已上架服务 | `CompanionServiceService.java:174-182`（`validateRefs` 校验 `enabled`）vs `:105-120`（`listBookable` 只过滤 `auditStatus` + `serviceStatus`） | 管理员停用某游戏后，该游戏**已上架的服务在用户端仍可见、仍可被预约**——"停用"没有达到预期效果 |
| **P7** | **停用游戏后仍可直接下单（API 层无校验）** | `OrderService.createOrder:71-92`：只校验"服务存在且归属一致（:74）→ 已过审且已上架（:77-80）→ 非自约（:82）→ 陪玩师可接单（:86-92）"，**全程未查询 `game.enabled`** | 即使按 P4 收口了 `listBookable`，只要拿到 `serviceId` 直接 `POST /api/orders` 依然能下单成功——"隐藏"只对界面成立、对 API 不成立。**P4 与 P7 必须同批修复，否则是"前端遮羞布"** |
| **P5** | **停用类型/标签的展示口径不一致** | 前台下拉会消失（`ServiceTypeService.java:30-35`、`TagService.java:38-46` 均过滤 `enabled=1`），但已创建服务仍按 ID 直取名称（`CompanionServiceService.java:219-220`，不校验 enabled） | 用户端仍展示"游戏教学"这类已停用类型；陪玩师编辑旧服务时下拉里找不到该类型，出现"选项不存在但值仍在"的错位 |
| **P6** | "类别"（标签分类）是硬编码枚举 | `TagCategory.java`：POSITION/STYLE/HERO/OTHER | 管理端即使做出标签页，也只能在四个既有分类内维护；是否要支持自定义分类见 10.1 |

## 4. 目标与非目标

### 4.1 目标

1. 管理员可在后台完成**游戏 / 服务类型 / 标签**的增删改查、排序与启用停用（FR-M10/M11/M12 全部有 UI，可截图进论文）。
2. 陪玩师只能**选择**管理员维护且已启用的目录项，且标签选择范围与其所选游戏匹配（不再能挂别的游戏的标签）。
3. 目录变更对已有业务数据安全：**停用优先、删除前引用校验**，误操作可逆。
4. 三端（管理端/陪玩端/用户端）对"已停用"的展示与生效口径一致。

### 4.2 非目标（本次不做）

- 不做"陪玩师申请新增类型 → 管理员审核"的流程（默认由管理员直接维护，见 10.5）。
- 不做标签批量导入、跨游戏复制（多游戏共用"打野/中单"仍需各建一条，见 10.2）。
- 不做标签分类的自定义配置（见 10.1）。
- 不动订单/钱包/评价/客服/AI 模块。

## 5. 方案总览

```
管理员后台【/admin/catalog】
  游戏管理 / 服务类型管理 / 标签管理
  新增 · 编辑 · 排序 · 启用停用 · 删除（带引用校验）
        │ 只看启用项
        ▼
陪玩师端【/companion/services 服务管理】
  选择游戏 → 服务类型（平台统一维护）→ 标签（仅该游戏 + 通用标签）
        │ 提交
        ▼
  服务审核（管理端 /admin/audit 服务项目 Tab）→ 陪玩师上架
        ▼
用户端【/games】【/companions】按启用目录浏览与预约
```

**停用/删除语义（本方案的收敛点）**：

| 对象 | 停用后 | 删除前校验 | 对已有数据 |
|---|---|---|---|
| 游戏 | 不再出现在陪玩师选择列表与用户端游戏页；**用户端「找陪玩」按游戏启用过滤，该游戏已上架服务自动隐藏**（可逆） | 存在陪玩服务引用 → 拒绝删除 | 历史订单使用下单快照，不受影响 |
| 服务类型 | 不再出现在陪玩师选择列表 | 存在服务引用 → 拒绝删除 | 已创建服务保留类型名，列表标注"已停用" |
| 标签 | 不再出现在陪玩师/用户端选择与展示 | 被陪玩师能力或服务引用 → 拒绝删除 | 已引用处的展示保留名称并标注"已停用" |

## 6. 详细设计

### 6.1 管理端新增页面：`/admin/catalog`（三 Tab）

**文件**：新建 `frontend/src/views/admin/CatalogManageView.vue`；`AdminLayout.vue:7-18` 菜单在「用户管理」后插入 `{ path: '/admin/catalog', label: '目录管理' }`；路由 `/admin/catalog`，`meta: { title: '目录管理' }`（`WorkbenchLayout` 的图标表补 `'目录管理': Files`）。

| Tab | 列 | 操作 |
|---|---|---|
| 游戏管理（FR-M10） | 名称、图标地址、简介、排序号、启用状态、更新时间 | 新增 / 编辑 / 启用停用（`el-switch`）/ 删除 |
| 服务类型管理（FR-M11） | 名称、编码、说明、排序号、启用状态 | 同上 |
| 标签管理（FR-M12） | 名称、分类（下拉）、所属游戏（下拉，"通用"=gameId 0）、排序号、启用状态 | 同上；支持按分类/游戏/关键词筛选 |

交互约定：

- 删除统一走 `ElMessageBox.confirm`，文案明确影响面（"该游戏已被 N 个陪玩服务引用，无法删除，请改为停用"由后端错误码驱动，见 6.4）。
- 启用状态用开关直接调 `PUT`，避免"编辑弹窗里改状态"的繁琐。
- 标签页的游戏下拉数据来自管理端游戏接口（含停用游戏，便于维护历史标签）。
- 表单校验与后端注解对齐（长度、排序号 0~9999、启用值 0/1），避免"前端放过、后端 400"。

### 6.3 陪玩侧收口

1. **标签按游戏过滤**（修 P2）：`ServiceManageView.vue` 的标签选项改为跟随 `form.gameId` 加载——切换游戏时清空已选标签、按新游戏拉取（复用申请页的 `tagOptions` 缓存写法，`BecomeCompanionView.vue:118-126`）；未选游戏时禁用标签下拉并提示"请先选择游戏"。
2. **来源提示**：服务类型与标签下拉加一行说明"由平台统一维护，如需新增类型请联系管理员"；下拉为空时用 `el-empty` 文案引导。
3. **不加**"申请新增类型"按钮（见 10.5）。

### 6.4 后端需要的改动（最小集，本方案后端**有**改动）

> 与前一个方案"后端零改动"不同：本次为了让"管理员维护目录"真正安全，需要 3 处小改动 + 1 处查询条件。

| 改动 | 文件 | 说明 |
|---|---|---|
| 删除前引用校验 | `GameService.deleteGame`、`ServiceTypeService.deleteType`、`TagService.deleteTag` | 存在引用时抛 `CATALOG_IN_USE`（409），提示改用停用。**校验范围见 6.4.1** |
| 停用游戏的可见性收口（修 P4） | `CompanionServiceService.listBookable:105-120` | 增加"游戏启用"过滤。实现方式：`inSql(game_id, "SELECT id FROM game WHERE enabled = 1")` 子查询（单条 SQL 完成，分页总数仍然正确；不用"查完再过滤"，那会破坏 `total`） |
| **停用游戏的下单收口（修 P7）** | `OrderService.createOrder:71-92` | 在"服务校验"之后补一步游戏校验：取出 `service.gameId` 对应游戏，`enabled != 1` 或不存在时抛 `SERVICE_NOT_AVAILABLE`(422)，消息"该游戏已停用，暂不可预约"。需为 `OrderService` 注入 `GameMapper`（当前未注入） |
| 停用类型/标签的展示口径（修 P5） | `CompanionServiceService.toView:203-233`；`ServiceView.java` | ① `ServiceView` 新增 `serviceTypeEnabled: Integer`；② **标签改用向后兼容方案**：保留 `tagNames: List<String>`（已启用标签名，现有三处消费方无需改动），新增 `disabledTagNames: List<String>`（已停用或已删除的标签名，取不到时回落 `标签#<id>`）。前端渲染为"名称 + 已停用标记" |
| 删除错误码 | `ErrorCode.java` | 新增 `CATALOG_IN_USE(409, "CATALOG_IN_USE", "该目录项已被引用，无法删除，请改为停用")`；具体对象在抛异常时用自定义 message 区分（如"该服务类型已被 3 个陪玩服务引用"） |

**不做**的改动：不改表结构、不改公开接口签名（`ServiceView` 只增字段不删字段）、不改权限模型（`AdminCatalogController` 的 `@PreAuthorize` 已正确）。

#### 6.4.1 引用校验的范围与取舍（明确写死，避免实施者与评审者各自脑补）

**校验范围 = 当前态数据**（会直接影响用户/陪玩师当下看到的页面）：

| 被校验对象 | 当前态引用来源 | 判定方式 |
|---|---|---|
| 游戏 | `companion_service.game_id` | 计数查询 |
| 游戏 | `companion_profile.capability_json[].gameId` | 读取资料后解析 JSON（陪玩师数量有限，Java 侧解析更精确） |
| 服务类型 | `companion_service.service_type_id` | 计数查询 |
| 标签 | `companion_service.tag_ids_json` | `JSON_CONTAINS(tag_ids_json, ?)`（该列是**真正的 MySQL JSON 列**，见 `sql/schema.sql:145`，可精确匹配，不会出现 `12` 命中 `112` 的误判） |
| 标签 | `companion_profile.capability_json[].positionTagIds` | 读取资料后解析 JSON |

**明确排除 = 历史快照**（保留但不校验，理由是"过严会导致任何被申请过的游戏/标签永久不可删"，而代价仅为展示降级）：

| 排除对象 | 为什么可以排除 |
|---|---|
| `companion_application.game_capability_json`（申请历史） | 历史记录按 ID 降级展示属可接受的展示损耗；申请页的"游戏能力"已按 `gameId` 回查游戏名（提交 `959e2fc` 修复过同款问题），删掉游戏后回落到 `游戏#<id>`，不影响审核与业务 |
| `play_order.game_id / service_type_id / 标签快照` | 订单只使用**下单快照**（`sql/schema.sql:181` 起多个 `*_snapshot` 字段），不依赖目录表存活；且**传递性覆盖成立**：任何下过单的游戏必然存在存活的 `companion_service`（服务不支持删除、只能下架），因此"服务引用校验"已经间接覆盖了订单维度 |
| `order_time_slot`、`order_status_history`、钱包流水等 | 与目录无外键关系，纯快照 |

> 实施与评审只需记住一句话：**删目录项会影响"现在正在用的地方"，不影响"历史记录里的文字"，后者的降级已被接受。**

## 7. 验收标准

### 7.1 正常链路（浏览器实跑）

1. 管理员进入 `/admin/catalog` → 游戏 Tab 新增「云顶之弈」并可编辑排序、停用/启用。
2. 服务类型 Tab 新增「排位上分」（编码 `RANK_BOOST`）→ 陪玩师端 `/companion/services` 新建服务时**下拉出现该类型**。
3. 标签 Tab 新增「云顶之弈」的 POSITION 标签「运营位」→ 陪玩师选择该游戏后**标签下拉出现「运营位」，且不再出现其它游戏的标签**（P2 验收）。
4. 陪玩师发布服务 → 管理员在 `/admin/audit` 服务项目 Tab 审核通过 → 上架 → 用户端可见。
5. 管理员把该服务类型停用 → 陪玩师新建服务时下拉不再出现；已上架服务在用户端仍展示类型名但标注"已停用"（按 6.5 口径）。
6. 管理员停用「云顶之弈」游戏 → 用户端 `/companions` 中该游戏的服务**不再出现**（P4 验收）；**并且拿着该服务的 `serviceId` 直接 `POST /api/orders` 返回 422 `SERVICE_NOT_AVAILABLE`**（P7 验收）；重新启用后两者均恢复。

### 7.2 异常分支

| 场景 | 操作 | 预期 |
|---|---|---|
| 删除被引用的游戏 | 删除已有服务的游戏 | 409 `CATALOG_IN_USE`，提示改为停用；游戏仍在 |
| 删除被引用的服务类型/标签 | 同上 | 409，删除被拒绝 |
| 删除无引用的目录项 | 删除刚建的测试类型 | 成功，且列表中消失 |

| 游客读取 | `GET /api/service-types` | 200，且**不含停用项** |
| 名称/编码重复 | 新增同名类型 | 409 `SERVICE_TYPE_NAME_EXISTS` / `SERVICE_TYPE_CODE_EXISTS` |
| 标签重复 | 同游戏同分类同名标签 | 409 `TAG_EXISTS` |

| 删除被"历史申请"引用的目录项 | 某用户申请过游戏 Y 但未通过/无资料，删除 Y | **允许删除**（历史快照被排除，申请时间线回落 `游戏#<id>`），这是刻意取舍 |

## 9. 风险与回滚

| 风险 | 说明 | 对策 |
|---|---|---|
| **删除按钮放开后产生脏引用** | 这是本方案最大风险：页面一上线，删除就可达 | **提交顺序已把护栏前置**：① 引用校验 → ② 管理页面，管理页面上线时后端已具备校验，不存在"接了没护栏接口"的中间态 |
| 停用游戏导致用户端服务消失 | P4 收口是行为变更 | 用"停用而非删除"的操作规范；管理端停用时提示"该游戏下有 N 个在架服务将同步隐藏"；P7 同批修复保证 API 口径与界面一致 |
| 后端首次进入本专题 | 与上一方案"后端零改动"不同 | 明确列出改动面（7 个文件，其中 5 个是 service/DTO，2 个是错误码与测试）；`mvn test` + 浏览器回归双验证 |
| `OrderService` 新增游戏校验可能影响既有订单链路 | 订单模块是最核心链路 | 校验只放在"创建订单"的第 2 步（服务校验之后），不触碰支付/履约/退款；97 项既有测试（含 `OrderModuleTest`、`CompanionModuleTest` 的订单闭环）作为回归证据 |
| 标签过滤改变陪玩师操作习惯 | 原有"全量标签"下已保存的服务标签可能包含他游戏标签 | 编辑旧服务时保留已选值并标注"已停用/不适用"，不强制清空 |
| 标签过滤改变陪玩师操作习惯 | 原有"全量标签"下已保存的服务标签可能包含他游戏标签 | 编辑旧服务时保留已选值并标注"已停用/不适用"，不强制清空 |
| 删除语义变化破坏既有 API 契约 | 原 `DELETE` 无条件成功 | 仅在"有引用"时新增 409；无引用行为不变，属于向后兼容的收紧 |

回滚方式：① ② 为前端改动，`git revert` 即可；③ 为后端改动，回滚后功能回到"删除无校验"的旧状态，但不会破坏数据（旧状态是宽松侧）。

## 10. 待确认事项（**已确认，2026-09-17**）

| # | 事项 | 决策 | 理由 |

| 1 | "服务类别"是否就是标签分类（POSITION/STYLE/HERO/OTHER）？是否把分类做成可配置？ | **是标签分类；分类不做可配置**，只管理标签本身 | 枚举作为系统边界、标签作为运营数据是站得住的设计决策（可写进论文）；可配置化要加表加 CRUD，收益配不上改动 |
