## 0. 摘要（先看这一页）

### 0.1 一句话结论

当前页面不是「打不开」，而是**「看不到现在、管不了长期、撤不回单日、保存会 422」**。本方案不改数据库核心模型，按「先修语义（救火）→ 再补能力（规则管理/续期/并发）→ 最后升级周看板」三步走，预计 5.5–7 人日。

### 0.2 核心决策（4 条）

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 默认时间范围 | **今天起 7 天**（不再是本周一至周日） | 页面目的是安排未来；周日打开时本周已无意义，也是「保存后像没生效」的根因 |
| 状态渲染 | **三态一等渲染**：可约 / 有单 / 休息 + 过期置灰 | 休息被吞是当前最直观的「页面坏了」；后端 overview 已返回 UNAVAILABLE，前端没渲染而已 |
| 长期规则管理 | **每条规则独立编辑**（按 templateId）+ 明示的规则列表/抽屉 | 现弹窗「工作日/周末两组」写死，默认值会凭空造规则，且丢失暂停/删除能力 |
| 续期与生成 | **按天幂等补齐**（替换水位线 gate）+ 每日定时任务 | 水位线「跳过即永久空洞」；幂等生成天然可重试，配合唯一键防并发重复 |

### 0.3 交付物

1. 前端：ScheduleView 重做（三态 + 今天起 7 天 + 规则管理 + 单日撤销）。
2. 后端：模板 update 语义修复、按天幂等生成、定时续期、restore-day 接口、RBAC、日志与审计。
3. SQL：新增 1 个迁移脚本（去重 + 幂等唯一键），同步 schema.sql。
4. 测试：后端 JUnit 用例 + 前端构建 + Playwright 验收脚本（由现有临时脚本改造）。
5. 文档：本方案 + 更新 README 功能说明。

| 阶段 | 内容 | 预估 | 可独立上线 |
| --- | --- | --- | --- |
| P0 | 前端三态/默认范围/规则管理/单日撤销 + 后端 update 语义/RBAC | 2.5 人日 | 是（前后端同批） |

## 3. 核心设计

### 3.1 数据与状态模型（不改核心表）

底层只有两类数据 + 一类叠加：

1. **长期作息模板** companion_availability_template：周几集合 + 每日时段（或全天）+ 生效区间 + enabled。
2. **档期实例** companion_availability：
   - AVAILABLE + RECURRENCE：模板生成的「可约底色」；
   - AVAILABLE + MANUAL：单日「额外可约」；
   - UNAVAILABLE + MANUAL：单日「休息」。
3. **订单占用** play_order / order_time_slot：叠加在可约之上的「已锁」。

**派生视图（前端统一算法）**：

~~~text
一天的时间轴 = 可约段（AVAILABLE）∪ 有单段（booked）∪ 休息段（UNAVAILABLE + 未被覆盖的空隙）
优先级：booked > available > off
过期：段结束时间 <= 服务器当前时间 → 置灰、不可操作
~~~

关键约定：

- 后端不需要新增「休息」语义字段；**没有 AVAILABLE 覆盖的时间天然不可约**，显式 UNAVAILABLE 只是给用户看的「主动休息」标记。
- 前端不再「只渲染 AVAILABLE、UNAVAILABLE 只做空行兜底」，而是先算全天覆盖，再打三段标签。
- 时间计算一律以 **overview 返回的 serverNow** 为准，避免用户设备时钟不准。

### 3.3 默认范围与导航

- 默认 rangeStart = **服务器今天 00:00**，显示 7 天（今天 ~ 今天+6）。
- 上一批/下一批按 7 天步进；范围限制在 [今天, 今天+28 天]，rangeStart=今天时「上一批」禁用。
- 「回到今天」在非今天范围时可用；在默认范围时禁用（当前页问题之一）。
- 页面显示「已安排至 X 月 X 日」（来自模板 lastGeneratedUntil），避免用户误以为可以无限往后翻。
- 今天之前不展示在默认范围；如保留历史视图，则整行置灰、无操作。

### 3.4 长期作息管理模型

**规则 = 一条模板**，弹窗一次只编辑一条（create/update），字段：

| 字段 | 控件 | 规则 |
| --- | --- | --- |
| 规则名称 | 输入框 | 默认「我的作息」；旧数据保留原名 |
| 生效周几 | 7 个可多选按钮（周一到周日） | 至少选 1 天；不限制「工作日/周末」 |
| 全天可约 | 开关 | 打开后隐藏时段选择 |
| 时段 | 开始/结束时间（HH:mm） | 不相等；结束早于开始 = 跨天，界面提示「次日 HH:mm」 |
| 生效开始 | 日期选择 | 新建 >= 今天；编辑展示原值且后端不因历史日期拒绝 |
| 生效结束 | 日期选择（可清空） | 空 = 长期；编辑时可清除（后端必须真清） |
| 启用状态 | 抽屉列表 switch | 与编辑解耦：编辑不改启停 |

校验（前端 + 后端双份）：至少一个周几；时段不相等；结束 >= 开始；同周几时段重叠给出 warning（不阻断）；名称长度 <= 50。

### 3.5 单日调整模型（可撤销）

| 当天现状 | 弹窗默认选项 | 可执行操作 | 调用 |
| --- | --- | --- | --- |
| 按长期作息（无手动记录） | 按长期作息 | 改为休息 / 加额外可约 | toggle-day-off(isOff=true) / POST /availabilities |
| 已休息（UNAVAILABLE） | 这天休息 | 恢复按作息 / 改休息时段（先恢复再休息） | POST /availabilities/restore-day |
| 有额外可约（MANUAL AVAILABLE） | 额外可约 | 删除额外 / 再添加一段 | DELETE /availabilities/{id} / POST /availabilities |
| 有订单的时段 | 不可修改 | 禁止覆盖该时段（后端已有订单校验） | — |
| 过去日期 | 禁止打开 | 无 | 前端禁用 |

**restore-day 语义**（新接口）：删除该日 MANUAL 记录 → 删除该日未被订单占用的模板实例 → 调 ensureWindow 重建该日；跨天手动记录 v1 返回 422「跨天单日调整暂不支持一键恢复」；任一待删记录与订单重叠返回 409。

### 3.6 生成与续期模型（核心：按天幂等）

现有实现是「水位线门控 + 首次访问补齐」，跳过日不会重试。改为**按天幂等补齐**：

~~~java
// AvailabilityTemplateService
@Transactional
public void ensureWindow(Long userId) {
    LocalDate today = LocalDate.now();
    LocalDate windowEnd = today.plusDays(GENERATE_WINDOW_DAYS); // 28 天

    // 锁住该陪玩师的模板行，串行化同一用户的并发生成
    List<CompanionAvailabilityTemplate> templates = templateMapper.selectList(
        new LambdaQueryWrapper<CompanionAvailabilityTemplate>()
            .eq(CompanionAvailabilityTemplate::getCompanionUserId, userId)
            .eq(CompanionAvailabilityTemplate::getEnabled, 1)
            .last("FOR UPDATE"));

    for (var t : templates) {
        LocalDate from = max(today, t.getEffectiveFrom());
        LocalDate to = min(windowEnd, t.getEffectiveUntil() == null ? windowEnd : t.getEffectiveUntil());
        for (LocalDate date = from; !date.isAfter(to); date = date.plusDays(1)) {
            if (!parseDays(t.getDayOfWeek()).contains(date.getDayOfWeek().getValue())) continue;
            Slot slot = slotOf(date, t);              // 全天 / 普通 / 跨天
            if (existsGenerated(t.getId(), slot.start)) continue;   // 已生成 → 幂等返回
            if (hasUnavailableOverlap(userId, slot)) continue;      // 用户休息优先
            if (hasAvailabilityOverlap(userId, slot)) continue;     // 已有可约（手动/其他规则）
            if (hasOrderOverlap(userId, slot)) continue;            // 订单优先
            insertRecurrence(t, slot);                // 唯一键兜底，捕获 DuplicateKey 忽略
        }
        t.setLastGeneratedUntil(to);                  // 仅用于「已安排至」展示
        templateMapper.updateById(t);
    }
}
~~~

要点：

- **不再用 lastGeneratedUntil 决定从哪天生成**，只用于展示；每次访问/保存/定时任务都按窗口逐日查漏补缺。
- 单日休息（UNAVAILABLE）作为「墓碑」：生成时检测到重叠就跳过，天然实现「休息覆盖模板」。
- 编辑模板：先 deleteFutureInstancesOfTemplate（保留有订单的），再 ensureWindow；失败/部分成功可下次自动修复。
- 性能：28 天 × 规则数（通常 1–3 条）查询量极小，可接受。
- 定时任务：每天 03:10 扫描所有 enabled 模板的 companion_user_id，逐个 ensureWindow；单个失败记日志不中断。

### 3.7 边界规则

| 场景 | 规则 |
| --- | --- |
| 今天已过去的时段 | 不生成/不显示为可约；手动创建 startAt 必须 >= now |
| 跨天时段（20:00–02:00） | 模板/额外时段均支持；预览按两天拆分并标注「次日」 |
| 单日休息与模板重叠 | 生成跳过该日；恢复后当天重新生成 |
| 订单与休息冲突 | 拒绝设休息（409，提示被锁定订单） |
| 多规则同日重叠 | 生成先到先得 + 另一条跳过；前端保存时提示重叠 |
| 超过 28 天 | 显示「已安排至 X 月 X 日」；边界外显示引导文案，不显示误导性空白 |
| 模板被暂停 | 立即清理未来未锁定实例；恢复时重新生成 |

### 4.3 关键算法（utils/schedule.ts）

~~~ts
export type SegmentKind = 'available' | 'booked' | 'off'

export interface DaySegment {
  kind: SegmentKind
  start: Dayjs
  end: Dayjs
  sourceType?: 'MANUAL' | 'RECURRENCE'
  availabilityId?: number
  booked?: BookedSlot
  expired: boolean
}

export function buildDay(date: Dayjs, overview: ScheduleOverview, now: Dayjs): DayView {
  // 1) 可约：所有 AVAILABLE 按天裁剪
  // 2) 休息标记：UNAVAILABLE 按天裁剪
  // 3) 订单：bookedSlots 按天裁剪
  // 4) 可约区间减去（订单 ∪ 休息）→ 真实可约；订单优先覆盖
  // 5) 剩余未覆盖区间 = off（区分「显式休息」与「未安排」）
  // 6) 合并相邻同类段、按 start 排序、标记 expired = end <= now
  return { date, weekday: date.day() === 0 ? 7 : date.day(),
           isToday: date.isSame(now, 'day'), segments, availableMinutes, bookedMinutes }
}
~~~

- 合并只合并**同 kind 且同 sourceType** 的相邻段（避免把「模板作息」和「单日额外」合成一块导致用户误解）。
- 段渲染：24h 时间条按分钟定位（left/width 百分比），今天段的 expired 加斜线纹理并禁止点击。

### 5.2 模板 create/update 校验拆分

~~~java
// 修改前：create 与 update 共用 validateAndBuild，update 也会拒绝历史 effectiveFrom（422 根因）
// 修改后：
private CompanionAvailabilityTemplate validateForCreate(Long userId, AvailabilityTemplateSaveRequest req) {
    if (req.getEffectiveFrom().isBefore(LocalDate.now())) {
        throw new BusinessException(ErrorCode.AVAILABILITY_TEMPLATE_PARAM_INVALID, "生效开始日期不能早于今天");
    }
    return build(userId, req);
}

private CompanionAvailabilityTemplate applyUpdate(CompanionAvailabilityTemplate existing,
                                                   AvailabilityTemplateSaveRequest req) {
    // 编辑场景：effectiveFrom 早于今天/为空 → 保留原值（绝不 422）
    if (req.getEffectiveFrom() != null && !req.getEffectiveFrom().isBefore(LocalDate.now())) {
        existing.setEffectiveFrom(req.getEffectiveFrom());
    }
    existing.setTemplateName(req.getTemplateName().trim());
    existing.setDayOfWeek(normalizeDays(req.getDayOfWeek()));
    existing.setAllDay(Boolean.TRUE.equals(req.getAllDay()) ? 1 : 0);
    existing.setStartTime(Boolean.TRUE.equals(req.getAllDay()) ? null : req.getStartTime());
    existing.setEndTime(Boolean.TRUE.equals(req.getAllDay()) ? null : req.getEndTime());
    existing.setEffectiveUntil(req.getEffectiveUntil());   // 允许 null
    return existing;
}

@Transactional
public AvailabilityTemplateView update(Long userId, Long id, AvailabilityTemplateSaveRequest req) {
    CompanionAvailabilityTemplate existing = requireOwned(userId, id);
    validateCommon(req);                                  // 时段/周几/区间合法性
    availabilityService.deleteFutureInstancesOfTemplate(userId, id);  // 保留有订单的
    CompanionAvailabilityTemplate updated = applyUpdate(existing, req);
    templateMapper.updateById(updated);
    ensureWindow(userId);
    return toView(templateMapper.selectById(id));
}
~~~

配套：

- 实体 effectiveUntil、startTime、endTime 加 @TableField(updateStrategy = FieldStrategy.ALWAYS)（或对这三个字段用 UpdateWrapper 显式 set null），否则 MyBatis-Plus 默认 NOT_NULL 会保留旧值。
- **不设置 enabled**；启停只走 /status 接口。
- deleteFutureInstancesOfTemplate 之后统一调 ensureWindow（按天幂等），不再依赖水位线。

### 5.3 按天幂等生成（替换 watermark gate）

见 3.6 代码骨架，补充实现细节：

1. existsGenerated(templateId, startAt)：SELECT COUNT(*) FROM companion_availability WHERE template_id = ? AND start_at = ?。
2. insertRecurrence：捕获 DuplicateKeyException 忽略（唯一键兜底）。
3. 新增/更新模板、暂停恢复、单日恢复、定时任务、页面 GET 都调用 ensureWindow（同一个幂等入口）。
4. lastGeneratedUntil 保留字段，仅写「窗口终点」用于页面展示；**不再参与是否生成的判断**（注释写清，避免后人恢复旧逻辑）。
5. 事务：ensureWindow 标 @Transactional；模板行 FOR UPDATE 保证同一用户串行；不同用户互不影响。
6. GET 侧建议每用户 5 分钟节流（本地 ConcurrentHashMap 时间戳即可，项目无 Redis 不引入）。

### 5.4 每日定时续期

~~~java
@Component
@RequiredArgsConstructor
@Slf4j
public class AvailabilityRenewTask {
    private final CompanionAvailabilityTemplateMapper templateMapper;
    private final AvailabilityTemplateService templateService;

    /** 每天 03:10 为所有启用模板的陪玩师补齐未来 28 天，避免长期不登录导致档期断档 */
    @Scheduled(cron = "0 10 3 * * *")
    public void renewAll() {
        List<Long> userIds = templateMapper.selectList(
                new LambdaQueryWrapper<CompanionAvailabilityTemplate>()
                    .eq(CompanionAvailabilityTemplate::getEnabled, 1)
                    .select(CompanionAvailabilityTemplate::getCompanionUserId))
            .stream().map(CompanionAvailabilityTemplate::getCompanionUserId).distinct().toList();
        for (Long userId : userIds) {
            try {
                templateService.ensureWindow(userId);
            } catch (Exception e) {
                log.warn("档期续期失败 userId={}", userId, e);
            }
        }
    }
}
~~~

GameCompanionApplication 已有 @EnableScheduling，无需新增配置。

### 5.5 restore-day 接口

~~~java
public record RestoreDayRequest(
        @NotNull @JsonFormat(pattern = "yyyy-MM-dd") LocalDate date) {}

@PostMapping("/restore-day")
public ApiResponse<RestoreDayResult> restoreDay(@Valid @RequestBody RestoreDayRequest req,
                                                Authentication authentication) {
    Long userId = currentUserId(authentication);
    return ApiResponse.ok(availabilityService.restoreDay(userId, req.date()));
}
~~~

实现：
1. 校验 date >= 今天（否则 422「不能恢复已经过去的日期」）。
2. 查该日 [00:00, 次日 00:00) 内的 MANUAL 记录（template_id=0）；若有跨天记录 → 422 提示先删除。
3. 逐条订单冲突检查，有冲突 → 409 AVAILABILITY_DELETE_FORBIDDEN（提示订单时段）。
4. 删除手动记录 + 该日由模板生成且未被订单占用的实例。
5. 调 ensureWindow(userId) 重新生成该日；返回 restoreDayResult{removedManual, removedGenerated, regenerated, skipped[]}。
6. 事务内完成；失败整体回滚。

### 6.1 迁移脚本（sql/migrations/20261018_availability_idempotent.sql）

~~~sql
-- 20261018_availability_idempotent.sql
-- 目标：为模板生成实例建立幂等唯一键，防止并发/重复生成；先清理历史重复数据。
-- 执行前请备份（deploy 脚本会自动备份 /opt/backup-<时间戳>）。

-- 1) 去重：同一陪玩师、同一模板、同一开始时间只保留 id 最小的一条
DELETE a FROM companion_availability a
JOIN companion_availability b
  ON a.companion_user_id = b.companion_user_id
 AND a.template_id = b.template_id
 AND a.start_at = b.start_at
 AND a.template_id > 0
 AND a.id > b.id;

-- 2) 生成列 + 唯一键：仅约束模板生成实例（template_id=0 时键为 NULL，MySQL 允许多个 NULL）
ALTER TABLE companion_availability
  ADD COLUMN recurrence_key VARCHAR(96)
    GENERATED ALWAYS AS (
      CASE WHEN template_id > 0
           THEN CONCAT(template_id, '@', DATE_FORMAT(start_at, '%Y-%m-%d %H:%i:%s'))
      END
    ) STORED COMMENT '模板生成实例幂等键（template_id>0 时生效）',
  ADD UNIQUE KEY uk_ca_recurrence (recurrence_key);
~~~

同步更新 sql/schema.sql：在 companion_availability 建表语句中加同样的生成列与唯一键（新库首次部署直接生效）。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 迁移加唯一键前存在重复实例 | 迁移失败 | 脚本先去重再加键；发布前在备份库演练 |
| 按天幂等生成改变「手动删除实例不回填」的旧行为 | 老用户习惯变化 | 用「这天休息」替代删除；文档与空态提示说明 |
| GET 触发 ensure 有写副作用 | 预取/重试引发写 | 幂等 + 行锁 + 每用户 5 分钟节流；P1 后以定时任务为主 |
| 订单数据保护逻辑在 0 订单环境下未被覆盖 | 上线后订单冲突 | 测试库造订单跑 restore-day/模板编辑；保留 409 提示 |
| 周时间网格（P2）工时超预期 | 延期 | 作为可选项，不阻塞 P0/P1；保留列表降级 |
| 前端一次改动较大 | 回归风险 | 拆提交、三宽度截图回归、Playwright 验收脚本 |

### D. 术语

| 术语 | 含义 |
| --- | --- |
| 长期作息 / 模板 | 按周几循环的默认可约规则（companion_availability_template） |
| 档期实例 | 模板生成或手动创建的具体时间记录（companion_availability） |
| 单日例外 | 用户对某一天做的休息/额外可约调整（MANUAL） |
| 水位线 | lastGeneratedUntil，旧续期机制；新方案仅用于展示 |
| 按天幂等 | 每次按「模板 × 日期」检查是否已生成，缺则补、不重复 |
| 三态 | 可约（绿）/ 有单（紫）/ 休息（灰） |
