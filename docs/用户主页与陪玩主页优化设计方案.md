# 用户主页与陪玩主页优化设计方案

| 项目 | 说明 |
|---|---|
| 适用范围 | 前端用户端 `/profile`（个人中心）、`/companions/:userId`（陪玩师详情）、陪玩师端 `/companion/profile`（主页维护） |
| 关联需求 | FR-U05（陪玩师详情 P0）、FR-U06（收藏 P1）、FR-U09（钱包）、FR-A04~A06（账号安全）、FR-P05/P06（陪玩主页） |
| 技术约束 | Vue 3 + TypeScript + Element Plus；沿用 `global.css` 原型设计令牌，不引入新框架 |
| 文档性质 | 设计方案（开发依据），实施前需按下文第 10 节分期推进 |

---

## 1. 现状盘点与差距分析

### 1.1 三个页面的现状

| 页面 | 文件 | 现状 |
|---|---|---|
| 个人中心 `/profile` | `views/user/ProfileView.vue` | 纯"设置页"：个人资料卡 + 钱包三格 + 陪玩中心状态卡 + 账号安全按钮组，全部为管理性质，无业务内容展示 |
| 陪玩师详情 `/companions/:userId` | `views/user/CompanionDetailView.vue` | 头部仅显示「陪玩师 #ID」与 emoji 占位头像；服务列表 + 评价列表（无分页、无评分汇总）；星级渲染存在逻辑瑕疵 |
| 陪玩主页维护 `/companion/profile` | `views/companion/CompanionProfileView.vue` | 编辑型工作台（接单状态 + 统计三格 + 资料表单），非展示页 |

### 1.2 差距分析（对照需求文档与代码事实）

1. **FR-U05（P0）未完整落地**：需求要求陪玩师详情展示"个人简介、能力标签、段位证明、服务项目、可约时间及历史评价"，当前页面缺失个人简介、段位证明（认证能力）、可约时间三类内容。根因：公开链路仅有 `GET /api/companion-services`（`BookableService` 不含 profile 数据），**缺少公开陪玩主页资料接口**。
2. **个人中心信息层次单一**：单列卡片堆叠，无 Hero 区、无 Tab 分区、无数据统计（订单数/评价数/收藏数）、无内容聚合（订单/评价/收藏均无入口），页面无浏览价值。
3. **FR-U06（P1）前端零接入**：后端 `FavoriteController` 已提供 `GET /api/favorites`、`POST/DELETE /api/favorites/{companionUserId}`，但前端无 `api/favorite.ts`、无任何页面引用。
4. **三套页面视觉割裂**：用户端使用原型组件类（`card`/`badge`/`two-col`/`detail-header`），陪玩师端使用 `el-card` 表单风格，缺乏统一的"主页"视觉语言。
5. **身份关联缺失**：同一用户的"个人中心"与"陪玩主页"之间无导航互通；陪玩师无法预览自己在用户端的展示效果。

## 2. 设计目标与原则

**目标**

1. 个人主页从"设置页"升级为"内容主页"：信息分层、可浏览、可导航。
2. 陪玩师公开主页补齐 FR-U05 要素，并与用户主页形成统一关联的展示体系。
3. 三套页面收敛到同一套组件与视觉语言，降低维护成本。

**原则**

- **一套骨架、两种视角、身份叠加**：所有主页共享统一骨架（Hero 身份区 + Tab 内容区）；本人视角侧重管理，访客视角侧重展示；陪玩师身份以 Tab 叠加进用户主页体系。
- **最小路由变更**：沿用 `/profile`、`/companions/:userId` 两个既有路由，不新增顶层路由分区。
- **数据先行**：先补公开资料接口（P0 缺口），前端展示层围绕既有接口排期；标注每个模块的数据支撑等级（现有可用 / 需后端补充 / 需求变更）。
- **沿用设计令牌**：主色 `#4285f4`、圆角 `0.5rem`、原型组件类体系全部保留，只做扩展不推翻。

## 3. 总体设计：统一主页体系

### 3.1 核心概念

```
统一主页骨架 ProfileShell
├── Hero 身份区（固定）：横幅 + 头像 + 名称 + 徽章 + 数据条 + 操作按钮
└── Tab 内容区（可扩展）：按身份与视角动态拼装
      ├── 普通用户本人：概览 | 订单 | 评价 | 收藏 | 钱包 | 设置
      ├── 陪玩师本人：  上述全部 + 陪玩主页（管理入口 + 公开预览）
      └── 访客看陪玩师：主页 | 服务 | 评价（即 /companions/:userId）
```

### 3.2 路由与视角映射

| 路由 | 视角 | 内容 | 鉴权 |
|---|---|---|---|
| `/profile` | 本人 | 个人主页（Tab 化，含管理功能） | 登录 |
| `/companions/:userId` | 访客/本人 | 陪玩师公开主页（游客可访问）；若 `userId` 为本人，Hero 追加「编辑主页」入口 | 无（游客可看） |
| `/companion/profile` | 本人（工作台） | 主页资料维护（保持编辑定位，新增「预览公开主页」按钮） | `COMPANION` |

### 3.3 组件复用体系（新增公共组件）

| 组件 | 用途 | 复用位置 |
|---|---|---|
| `ProfileHero` | 身份头部（横幅/头像/名称/徽章/数据条/操作） | 个人主页、陪玩公开主页 |
| `StatStrip` | 横向数据统计条 | 两处 Hero、概览 Tab |
| `CompanionCard` | 陪玩师信息卡 | 找陪玩列表、收藏 Tab、概览推荐位 |
| `CapabilityCard` | 游戏能力认证卡（游戏 + 区服 + 段位 + 位置标签） | 陪玩公开主页、我的陪玩主页 Tab |
| `ServiceCardGrid` | 服务项目卡片网格（含选中态） | 陪玩公开主页 |
| `RatingHistogram` | 评分分布直方图 + 高频标签 | 陪玩公开主页评价区 |
| `StatusDot` | 接单状态灯（绿/黄/灰/红） | 陪玩公开主页、陪玩师工作台 |
| `SectionSkeleton` | 骨架屏 | 所有懒加载 Tab |
| `GuidedEmptyState` | 引导性空状态（文案 + 行动按钮） | 全部列表空态 |

## 4. 用户个人主页（`/profile`）结构规划

### 4.1 页面骨架（三层）

```
┌──────────────────────────────────────────────┐
│ L1  Hero 身份区                                │
│     渐变横幅（primary → #dbeafe 线性渐变）       │
│     头像 96px | 昵称 + 角色徽章 + 账号状态       │
│     数据条：订单 | 评价 | 收藏 | 注册天数         │
│     操作：[编辑资料] [账号安全]                   │
├──────────────────────────────────────────────┤
│ L2  Tab 导航（sticky 吸顶）                     │
│     概览 | 订单 | 评价 | 收藏 | 钱包 | 设置        │
│     （陪玩师追加「我的陪玩主页」Tab，带状态灯）     │
├──────────────────────────────────────────────┤
│ L3  Tab 内容区（懒加载，URL hash 同步）          │
└──────────────────────────────────────────────┘
```

### 4.2 Hero 身份区

- 横幅：CSS 线性渐变 `linear-gradient(135deg, var(--primary), #6d5efc)`，叠加大号低透明度游戏图标纹理（纯 CSS/SVG，零图片资源成本）。
- 头像：沿用 `el-avatar`，加载失败回退昵称首字母。
- 数据条（`StatStrip`）：已完成订单数、累计评价数、收藏的陪玩师数、注册天数。
- 陪玩师用户在 Hero 右侧追加**陪玩身份卡**：状态灯 + 展示名 + 评分 + 完成单数 + [预览公开主页] 按钮。

### 4.3 Tab 分区与模块明细

| Tab | 内容 | 数据支撑 | 等级 |
|---|---|---|---|
| **概览** | ① 资料完整度引导卡（头像/简介/手机/邮箱四项检测，缺失项一键跳转编辑）② 近期订单时间线（最近 5 条，状态徽章着色）③ 收藏的陪玩师横滑卡（`CompanionCard` 精简版）④ 钱包概览（保留现有三格）⑤ 陪玩中心成长卡（原"陪玩中心"五态升级） | 订单接口、`GET /api/favorites`、`walletMe`、`myProfile`、`myApplications` | 现有可用（收藏需前端首次接入） |
| **订单** | 我的订单列表（状态筛选 Tab：全部/待支付/进行中/待评价/已完成），复用 `OrdersView` 抽取的 `OrderListPanel` 组件 | 现有订单分页接口 | 现有可用 |
| **评价** | 我发出的评价列表（星级 + 标签 + 内容 + 关联订单号），支持删除前查看关联订单 | `myReviews`（已存在） | 现有可用 |
| **收藏** | 收藏的陪玩师网格（`CompanionCard`：头像/展示名/评分/标签/起价/接单状态），支持取消收藏（乐观更新 + 失败回滚） | `GET /api/favorites`（后端已实现，前端待接入） | 后端就绪，前端新增 |
| **钱包** | 余额/冻结/累计收入大卡 + 收支流水明细（分页） | `walletMe`（流水明细接口需核对，若无需后端补充） | 部分依赖核对 |
| **设置** | 账号安全（修改密码/注销全部会话/退出登录）+ 资料编辑对话框入口（迁移现有功能，逻辑不变） | 现有接口 | 现有可用 |
| **我的陪玩主页**（仅陪玩师） | ① 接单状态快捷切换（沿用现有 radio 逻辑）② 公开数据看板（评分/评价数/完成单/服务数）③ 认证能力卡（`CapabilityCard` 只读态）④ [预览公开主页] 大按钮 → `/companions/:myUserId` ⑤ [去工作台维护资料] → `/companion/profile` | `myProfile`、`listMyServices` | 现有可用 |

**懒加载策略**：仅概览 Tab 随页面首屏加载，其余 Tab 首次激活时请求；Tab 状态写入 URL hash（`/profile#tab=orders`），刷新/分享后定位一致。

## 5. 陪玩师公开主页（`/companions/:userId`）设计

### 5.1 页面骨架

```
┌──────────────────────────────────────────────┐
│ Hero 身份区                                    │
│   封面横幅 | 头像 88px | 展示名 + 认证徽章       │
│   接单状态灯（可接单/忙碌/休息中/暂停）           │
│   数据条：评分 | 完成单 | 服务数 | 起价           │
│   操作：[立即预约] [♥ 关注]（本人访问显示[编辑主页]）│
├───────────┬──────────────────────────────────┤
│ 侧栏 sticky │ Tab: 主页 | 服务 | 评价            │
│           │                                  │
│ 能力认证    │ 主页 Tab: 主页简介 + 能力认证卡     │
│ 认证徽章    │ 服务 Tab: 服务卡片网格（选中态）     │
│ 服务标签    │ 评价 Tab: 评分分布 + 高频标签 + 列表 │
│ 未来档期    │                                  │
│ [立即预约]  │                                  │
└───────────┴──────────────────────────────────┘
```

### 5.2 模块明细

| 模块 | 设计要点 | 数据支撑 | 等级 |
|---|---|---|---|
| **Hero 身份区** | 展示名（替代「陪玩师 #ID」）、真实头像（替代 emoji 占位）、认证徽章、接单状态灯、评分/完成单/服务数/起价数据条；本人访问追加「编辑主页」入口 | **缺公开 profile 接口**，建议新增 `GET /api/companion-profiles/{userId}`（仅返回认证通过且非封禁的公开字段：displayName、avatarUrl、profileIntro、serviceStatus、ratingAvg、ratingCount、completedOrderCount、capabilities） | **需后端补充（P0）** |
| **主页 Tab** | ① `profileIntro` 段落展示（空态引导文案）② 能力认证卡 `CapabilityCard`：游戏名 + 区服 + 段位徽章 + 位置标签（FR-U05 的"段位证明"）③ 服务标签云 | 同上公开 profile 接口 | **需后端补充（P0）** |
| **服务 Tab** | 行式列表升级为卡片网格（2 列）：游戏/类型徽章 + 标题 + 描述 + 标签 + 价格（¥/小时）+ 最短时长；选中态高亮（主色边框 + 浅底）；底部吸附预约条显示已选服务与合计价 | `listBookableServices`（现有） | 现有可用 |
| **评价 Tab** | ① 评分汇总：平均分大数字 + `RatingHistogram` 五档分布条形图（前端聚合当前页数据）② 高频评价标签云 ③ 评价列表分页（修复现有星级渲染逻辑，补充筛选：全部/5 星/4 星及以下） | `companionReviews`（现有，前端聚合分布） | 现有可用 |
| **未来档期（侧栏）** | 未来 7 天可约时段紧凑条形图（绿=可约/灰=不可约），点击时段直达预约页并预填时间 | **缺公开档期接口**，建议 `GET /api/companion-profiles/{userId}/availabilities?days=7`（仅返回 AVAILABLE 时段，不含备注） | **需后端补充（P1，FR-U05"可约时间"）** |
| **关注按钮** | Hero 与侧栏双入口；未登录点击引导登录；乐观更新 + 失败回滚 | `POST/DELETE /api/favorites/{companionUserId}`（后端已实现） | 后端就绪，前端新增 |

### 5.3 预约动线优化

- 选中服务 → 侧栏「立即预约」按钮实时显示已选服务名与单价；未选中时默认取价格最低项。
- 档期图点击时段 → `/booking?companionUserId=&serviceId=&startAt=` 预填预约时间。
- 全程无跳转流失点：服务选中状态在 Tab 切换间保持。

## 6. 两者的衔接设计

### 6.1 身份融合

- 陪玩师的**个人主页**与**公开陪玩主页**共用 `ProfileHero` / `StatStrip` / `CompanionCard` 组件，数据条结构同构（评分、单量、收藏数口径一致）。
- 陪玩师本人视角：个人主页 Hero 陪玩身份卡 + 「我的陪玩主页」Tab → 承载管理与数据看板；`/companions/:myUserId` → 承载"用户端真实展示效果"。
- 访客视角：只看到公开陪玩主页，不暴露任何管理入口。

### 6.2 导航互通矩阵

| 起点 | 交互 | 终点 |
|---|---|---|
| 个人主页 Hero 陪玩身份卡 | [预览公开主页] | `/companions/:myUserId` |
| 个人主页「我的陪玩主页」Tab | [去工作台维护资料] | `/companion/profile` |
| 陪玩公开主页（本人访问） | [编辑主页] | `/companion/profile` |
| 陪玩工作台 `/companion/profile` | [预览用户端展示效果]（新增按钮） | `/companions/:myUserId` |
| 订单详情（已完成） | [查看陪玩主页] | `/companions/:companionUserId` |
| 收藏卡片 / 找陪玩列表 | 点击卡片 | `/companions/:userId` |

### 6.3 入驻漏斗（陪玩中心成长卡）

保留现有五态状态机（`NEW / PENDING / REJECTED / APPROVED / COMPANION`），视觉升级为**进度条式成长卡**：

```
[① 提交申请] ──→ [② 平台审核] ──→ [③ 维护主页] ──→ [④ 上架服务] ──→ [⑤ 开始接单]
```

- 未申请：进度 0，突出「成为陪玩师」主按钮 + 收益预期文案。
- 审核中：进度 1/5，显示提交时间与预计时效。
- 已驳回：进度 1/5 + 驳回原因 + 「修改后重新提交」。
- 已通过未入驻资料：进度 2/5，引导「进入工作台维护主页」。
- 已是陪玩师：满格状态，显示核心数据（完成单/评分）+ 双入口（工作台/公开主页预览）。

### 6.4 收藏联动（FR-U06 前端落地）

- 陪玩公开主页、找陪玩列表卡片的「关注」按钮共用一个 `useFavorite` 组合式函数（内部管理乐观更新与登录校验）。
- 收藏成功 → 个人主页 Hero 数据条「收藏」计数 +1（响应式联动）。
- 概览 Tab 收藏横滑区提供「查看全部」→ 收藏 Tab。

## 7. 视觉风格规范

### 7.1 设计令牌扩展（追加至 `global.css`，不改动既有令牌）

```css
:root {
  /* 状态灯（接单状态） */
  --status-available: #16a34a;   /* 可接单 */
  --status-busy: #f59e0b;        /* 忙碌 */
  --status-resting: #94a3b8;     /* 休息中 */
  --status-suspended: #ef4444;   /* 暂停接单（管理员设置） */

  /* Hero 横幅渐变 */
  --hero-gradient: linear-gradient(135deg, #4285f4, #6d5efc);

  /* 层次阴影（三级） */
  --shadow-hero: 0 8px 24px rgba(15, 23, 42, 0.12);
  --shadow-card: 0 1px 2px rgba(15, 23, 42, 0.04);
  --shadow-hover: 0 8px 24px rgba(15, 23, 42, 0.08);

  /* 段位徽章底色（复用 badge 体系） */
  --rank-gold: #f59e0b;
}
```

### 7.2 信息层次三级制

| 层级 | 载体 | 视觉 |
|---|---|---|
| L1 主层 | Hero 身份区 | 渐变横幅、大头像、`--shadow-hero`、数据条 24px 数字 |
| L2 内容层 | 各 Tab 卡片 | 白底 + `--border` 边框 + `--shadow-card`，标题 1.125rem/600 |
| L3 微层 | 卡片内分组、标签、徽章 | `--muted` 底、12px 说明文字、badge 体系 |

### 7.3 状态与徽章系统

- 接单状态灯：8px 圆点 + 呼吸动画（仅 AVAILABLE），文案徽章同色系浅底。
- 认证徽章：蓝底「已认证」；段位徽章：金底，取能力卡最高段位展示于 Hero。
- 角色徽章沿用 `badge-secondary`，账号状态沿用 `badge-success/warning`。

### 7.4 通用体验规范

- **骨架屏**：所有懒加载 Tab 首次进入显示 `SectionSkeleton`（替代全局 `v-loading` 遮罩）。
- **空状态**：`GuidedEmptyState` 统一「图标 + 一句话 + 行动按钮」，如订单空态 →「去逛逛陪玩师」按钮直达 `/companions`。
- **图片兜底**：头像/封面加载失败回退首字母色块（以用户名首字符哈希取色）。
- **动效克制**：Tab 内容 fade-in 120ms；卡片 hover 上浮 2px；状态灯呼吸 2s 循环；遵循 `prefers-reduced-motion`。

## 8. 交互优化建议

1. **Tab 与 URL 同步**：`/profile#tab=orders`、`/companions/1#tab=reviews`，支持刷新保持、直接分享锚点。
2. **sticky 吸顶**：Tab 导航滚过 Hero 后吸顶（`position: sticky`，带底部阴影提示层级）。
3. **预约吸底条**：移动端选中服务后底部吸附「已选 XX 服务 ¥XX/小时 | 去预约」，桌面端固化于侧栏。
4. **乐观更新**：关注/取消关注、接单状态切换均先更新 UI 再请求，失败回滚 + Toast。
5. **评价交互**：筛选（全部/好评/中差评）+ 分页；星级渲染修复为标准五星组件逻辑。
6. **横滑与懒加载**：收藏横滑区 `overflow-x: auto` + 隐藏滚动条；列表图片 `loading="lazy"`。
7. **响应式断点**：≥992px 双栏（侧栏+内容）；768~992px 侧栏折叠为顶部能力卡横滑；<768px 单栏 + 底部吸底预约条。

## 11. 边界与风险

1. **公开接口信息泄露**：公开 profile 接口必须过滤真实姓名、手机号等入驻资料（`Application` 中的敏感字段不得外泄），仅返回 `CompanionProfile` 白名单字段。
2. **游客可见性**：`/companions/:userId` 保持游客可访问，关注/预约按钮对游客做登录引导而非隐藏。
3. **数据一致性**：本人预览公开主页时，编辑保存后需刷新公开接口缓存（当前无缓存，风险低，如实标注）。
4. **`BookableService` 聚合的临时方案**：P0-a 接口落地前，前端可用服务列表聚合出"服务数/起价"，但展示名/头像/简介**无法**从现有接口获得，不可跳过 P0-a。
5. **评价分布准确性**：前端按页聚合评分分布仅统计已加载评价，标注"基于最近 N 条"；精确分布需后端聚合接口（P2）。
6. **需求文档一致性**：毕设项目需保持文档与实现同步，P0/P1 均在既有 FR 条目范围内；作品/动态模块必须先走需求变更流程。
